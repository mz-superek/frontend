1. 학습 목표 (심화)

기초편이 "API 문서를 읽고 구현하며 디버깅하는 수준"이었다면, 심화편은 그 윗단계입니다. 같은 API를 보더라도 왜 이렇게 설계됐는지, 무엇이 위험한지, 더 나은 방법은 무엇인지를 읽어냅니다.

설계 의도 읽기동시성성능보안백엔드 협업 심화

최종적으로 할 수 있어야 하는 말

"이 결제 API는 재시도 시 중복 결제를 막아야 하니 Idempotency-Key가 필요하고, 토큰은 XSS를 고려해 저장 위치를 정해야 하며, 목록은 데이터가 자주 바뀌니 cursor 페이지네이션이 맞다. 그리고 이 화면은 세 API를 병렬로 받아도 되니 Promise.all로 묶고, 느린 하나는 Suspense로 분리한다."

2. HTTP 버전과 연결: 1.1 / 2 / 3, TLS

같은 REST API라도 어떤 HTTP 버전 위에서 도느냐에 따라 성능 특성이 달라집니다.

버전 전송 핵심
HTTP/1.1 TCP 연결당 요청을 순서대로 처리. 한 요청이 느리면 뒤가 막힘(head-of-line blocking). 그래서 브라우저가 도메인당 연결을 6개쯤 엶
HTTP/2 TCP 하나의 연결에서 여러 요청을 동시에 주고받음(멀티플렉싱). 헤더 압축(HPACK). 단, TCP 레벨의 HOL blocking은 남음
HTTP/3 QUIC (UDP) TCP를 버리고 UDP 기반 QUIC 사용. 패킷 손실이 한 스트림만 막고 나머지는 진행 → 모바일·불안정 네트워크에서 유리
프론트에서 볼 포인트

HTTP/2 이상에서는 "요청 여러 개로 쪼개면 느려진다"는 1.1 시절 통념이 약해집니다. 번들을 무조건 하나로 합치기보다 캐시 효율을 고려해 나누는 전략도 가능해집니다. Network 탭의 Protocol 열에서 h2, h3를 확인할 수 있습니다.

HTTPS와 TLS

HTTPS는 HTTP를 TLS로 암호화한 것입니다. 브라우저와 서버는 본 통신 전에 핸드셰이크로 암호 키를 교환합니다.

클라이언트 Hello ↓ 서버 인증서 전달 ↓ 키 교환 ↓ 이후 통신 암호화

TLS 1.3은 핸드셰이크를 1-RTT로 줄여 더 빠릅니다. 인증서가 만료·불일치하면 브라우저가 연결을 막고, 이때 API 호출은 응답 코드도 못 받고 네트워크 에러로 실패합니다(상태 코드 없음).

3. 캐싱 심화: Cache-Control · ETag

"왜 옛날 데이터가 보이지?"의 절반은 HTTP 캐시에서 결정됩니다. (나머지 절반은 React Query 캐시.)

Cache-Control 주요 값

값 의미
max-age=600 600초 동안은 재요청 없이 캐시 사용
no-cache 캐시는 두되, 쓰기 전 서버에 "바뀌었나" 검증(조건부 요청)
no-store 아예 저장 금지. 민감 정보에 사용
private / public private은 브라우저만, public은 CDN 등 중간 캐시도 저장 가능
must-revalidate 만료되면 반드시 서버 검증 후 사용

ETag로 트래픽 줄이기

ETag는 응답 본문의 "지문"입니다. 클라이언트가 다음 요청에 그 지문을 보내면, 안 바뀌었을 때 본문 없이 304만 옵니다.

// 1차 응답
200 OK
ETag: "v3-abc"

// 2차 요청 (클라이언트가 지문 첨부)
GET /users
If-None-Match: "v3-abc"

// 안 바뀌었으면 → 본문 없이
304 Not Modified
프론트에서 볼 포인트

304는 "성공이지만 캐시 쓰라"는 뜻이라 정상입니다. 또 stale-while-revalidate는 "일단 캐시를 바로 보여주고 뒤에서 조용히 새로 받아오라"는 전략으로, 사용자 체감 속도를 올리는 데 자주 쓰입니다.

4. REST 성숙도 & API 설계 심화

Richardson 성숙도 모델

REST가 얼마나 "REST다운가"를 4단계로 봅니다. 실무 API가 어느 수준인지 가늠하는 기준이 됩니다.

레벨 특징
Level 0 엔드포인트 하나에 전부 POST (사실상 RPC). 예: POST /api
Level 1 리소스별 URL 분리. 예: /users, /orders
Level 2 HTTP Method와 상태 코드를 의미대로 사용. 대부분의 실무 REST API가 여기
Level 3 응답에 다음 행동 링크 포함(HATEOAS). 예: 주문 응답에 "취소" 링크가 함께 옴

Idempotency Key (멱등 키)

POST는 원래 멱등하지 않아서, 결제 요청이 네트워크 지연으로 재시도되면 중복 결제가 날 수 있습니다. 이를 막으려고 클라이언트가 요청마다 고유 키를 보내고, 서버는 같은 키의 재시도를 한 번만 처리합니다. 

POST /payments
Idempotency-Key: 9f1c-2a7e-...   // 재시도해도 같은 키 → 1회만 결제
프론트에서 볼 포인트

결제·주문 같은 "두 번 일어나면 안 되는" 요청에 재시도 로직을 넣을 땐, 매번 새 키가 아니라 같은 시도엔 같은 키를 보내야 합니다.

버저닝 전략

방식 예시 특징
URL 경로 /v1/users 가장 흔하고 눈에 잘 보임
헤더 Accept: application/vnd.api+json;version=1 URL은 깔끔하지만 디버깅 시 잘 안 보임

페이지네이션 deep: cursor / keyset

offset 방식(?page=2)은 큰 데이터에서 느리고, 중간에 행이 추가·삭제되면 누락·중복이 생깁니다. cursor(keyset) 방식은 "마지막으로 본 값 이후"를 조건으로 잡아 이를 피합니다.

// offset: 앞 100개를 건너뛰고 세어야 함 → 뒤로 갈수록 느림
SELECT * FROM posts ORDER BY id DESC LIMIT 20 OFFSET 100;

// keyset(cursor): 마지막 본 id 기준 → 항상 빠름
SELECT * FROM posts WHERE id < 880 ORDER BY id DESC LIMIT 20;

에러 응답 설계

좋은 API는 에러도 일관된 구조로 줍니다. 표준으로 application/problem+json(RFC 7807)이 있습니다.

{
  "type": "https://api.co/errors/invalid-field",
  "title": "Validation failed",
  "status": 422,
  "detail": "email 형식이 올바르지 않습니다",
  "errors": [{ "field": "email", "message": "invalid format" }]
}
프론트에서 볼 포인트

에러 메시지를 화면에 띄울 때 message가 어디 있는지(최상위인지 errors[].message인지)를 문서에서 먼저 확인하세요. 필드별 에러를 폼 입력칸 아래에 매핑하려면 field 키가 필요합니다.

Rate Limiting (429)

서버는 과도한 호출을 429로 막고, 언제 다시 시도할지 헤더로 알려줍니다.

429 Too Many Requests
Retry-After: 30          // 30초 뒤 재시도
X-RateLimit-Remaining: 0 // 남은 호출 수

재시도는 일정 간격이 아니라 지수 백오프 + 지터(1초→2초→4초에 무작위를 더함)로 하면 서버 부하 폭주를 막을 수 있습니다.

5. OAuth 2.0 / OIDC

"카카오로 로그인", 사내 SSO 뒤에 있는 표준입니다. 핵심 구분부터 잡습니다.

표준 목적 결과물
OAuth 2.0 인가 — "이 앱이 내 자원에 접근해도 됨" Access Token
OIDC 인증 — "이 사용자가 누구인지"를 OAuth 위에 얹음 ID Token (JWT)

Authorization Code + PKCE

SPA·모바일처럼 비밀키를 숨길 수 없는 환경에서 쓰는 표준 흐름입니다.

앱이 code_verifier 생성 → 해시(code_challenge)와 함께 인가 서버로 이동 ↓ 사용자 로그인·동의 ↓ 인가 코드(code) 수신 ↓ code + 원본 code_verifier로 토큰 교환 ↓ Access Token (+ Refresh Token, OIDC면 ID Token)
왜 PKCE인가

인가 코드가 중간에 탈취돼도, 원본 code_verifier가 없으면 토큰으로 교환할 수 없습니다. 그래서 클라이언트 비밀키 없이도 안전합니다. 과거 SPA에서 쓰던 Implicit 방식은 지금은 권장되지 않습니다.

주요 Grant Type

  • Authorization Code (+PKCE): 사용자 로그인이 있는 웹·앱. 가장 일반적
  • Client Credentials: 사용자 없이 서버↔서버 통신
  • Refresh Token: 만료된 Access Token 재발급

6. 토큰 전략: Access / Refresh Rotation

왜 둘로 나누나

Access Token은 자주 쓰여서 탈취 위험이 크니 수명을 짧게(분 단위), Refresh Token은 안전하게 보관하며 수명을 길게 둡니다. Access가 만료되면 Refresh로 새로 받습니다.

Refresh Token Rotation

재발급할 때마다 Refresh Token도 새것으로 바꾸고 이전 것은 폐기합니다. 만약 이미 폐기된(이전) Refresh가 다시 쓰이면 = 탈취 신호로 보고 해당 세션 전체를 무효화합니다.

Access 만료 ↓ Refresh로 재발급 요청 ↓ 새 Access + 새 Refresh 발급, 옛 Refresh 폐기 ↓ (옛 Refresh가 다시 등장하면) 탈취 의심 → 전체 로그아웃

토큰 저장 위치 트레이드오프

위치 장점 위험
localStorage 다루기 쉬움 XSS로 JS가 읽어가면 탈취됨
httpOnly Cookie JS가 못 읽음 → XSS에 강함 CSRF 고려 필요(SameSite로 완화)
메모리(변수) 탈취 표면 최소 새로고침하면 사라짐 → Refresh로 복구 설계 필요
현실적인 절충안

Access Token은 메모리에, Refresh Token은 httpOnly + Secure + SameSite 쿠키에 두는 조합이 많이 쓰입니다. "정답"이라기보다 위협 모델에 따른 선택이라는 점을 이해하는 게 핵심입니다.

7. 웹 보안: XSS · CSRF · CORS · CSP

XSS (Cross-Site Scripting)

공격자가 심은 스크립트가 다른 사용자의 브라우저에서 실행되는 공격입니다.

  • Stored: 게시글 등 서버에 저장된 악성 스크립트
  • Reflected: URL 파라미터 등이 그대로 화면에 출력될 때
  • DOM 기반: 프론트 JS가 입력값을 DOM에 직접 꽂을 때
프론트 방어

React·Vue는 기본적으로 출력값을 이스케이프합니다. 위험은 dangerouslySetInnerHTML, v-html처럼 그 보호를 끄는 지점입니다. 외부 입력을 그대로 넣지 말고, 필요하면 DOMPurify 같은 도구로 정제하세요.

CSRF (Cross-Site Request Forgery)

로그인된 사용자의 쿠키를 이용해, 사용자도 모르게 요청을 보내게 만드는 공격입니다. 쿠키 인증에서 특히 문제됩니다.

방어 설명
SameSite=Lax/Strict 다른 사이트에서 온 요청에는 쿠키를 안 붙임 (1차 방어선)
CSRF 토큰 폼·요청마다 예측 불가한 토큰을 함께 검증

CORS Preflight 심화

"단순 요청"이 아닌 경우, 브라우저가 본 요청 전에 OPTIONS로 미리 허락을 묻습니다(preflight).

// 아래 중 하나라도 해당하면 preflight 발생
- PUT, DELETE, PATCH 등
- Content-Type: application/json (단순 타입이 아님)
- Authorization 등 커스텀 헤더

OPTIONS /users
→ 서버가 허용 응답:
Access-Control-Allow-Methods: PUT, DELETE
Access-Control-Allow-Headers: Authorization, Content-Type
Access-Control-Max-Age: 600   // preflight 결과 캐시
프론트에서 볼 포인트

"GET은 되는데 PUT/DELETE만 막힌다"면 거의 preflight 설정 문제입니다. Network 탭에 본 요청 앞에 OPTIONS 요청이 보이는지 확인하세요. 해결은 보통 서버에서 합니다.

CSP (Content-Security-Policy)

실행 가능한 스크립트 출처를 제한하는 헤더입니다. XSS의 영향 범위를 줄이는 마지막 방어선 역할을 합니다.

Content-Security-Policy: script-src 'self' https://cdn.trusted.com

8. 실시간 통신: Polling · SSE · WebSocket

"실시간 알림", "라이브 상태"를 구현할 때 선택지입니다. 양방향이 필요한지부터 따집니다.

방식 방향 특징 / 적합한 곳
Polling 단방향 (요청 반복) 일정 간격으로 계속 요청. 단순하지만 낭비 많음. 가벼운 갱신
Long Polling 단방향 응답을 변화가 생길 때까지 잡아둠. 폴링보다 효율적
SSE 서버 → 클라이언트 HTTP 위에서 서버가 일방적으로 푸시. 자동 재연결. 알림·피드에 적합
WebSocket 양방향 연결을 열고 서로 자유롭게 송수신. 채팅·협업·게임에 적합 
// SSE — 브라우저 기본 API로 간단
const es = new EventSource("/notifications");
es.onmessage = (e) => console.log(e.data);
// 연결이 끊겨도 자동으로 재연결을 시도합니다
선택 기준

클라이언트가 서버로도 자주 보내야 하면 WebSocket, 서버가 일방적으로 알려주기만 하면 SSE면 충분합니다. 굳이 양방향이 필요 없는데 WebSocket을 쓰면 인프라만 복잡해집니다.

9. 데이터 레이어 심화: React Query

기초편의 useQuery/useMutation을 넘어, 실무에서 자주 쓰는 패턴입니다.

queryKey 팩토리

키를 문자열로 흩뿌리면 오타·무효화 누락이 생깁니다. 한 곳에서 관리하세요.

export const userKeys = {
  all: ["users"],
  list: (filters) => ["users", "list", filters],
  detail: (id) => ["users", "detail", id],
};
// 무효화: queryClient.invalidateQueries({ queryKey: userKeys.all })

Optimistic Update (롤백 포함)

useMutation({
  mutationFn: toggleLike,
  onMutate: async (next) => {
    await queryClient.cancelQueries({ queryKey: ["post", id] });
    const prev = queryClient.getQueryData(["post", id]);
    queryClient.setQueryData(["post", id], next); // 먼저 반영
    return { prev };
  },
  onError: (e, next, ctx) => {
    queryClient.setQueryData(["post", id], ctx.prev); // 실패 시 롤백
  },
  onSettled: () => queryClient.invalidateQueries({ queryKey: ["post", id] }),
});

Infinite Query (무한 스크롤)

useInfiniteQuery({
  queryKey: ["posts"],
  queryFn: ({ pageParam }) => api.get(`/posts?cursor=${pageParam ?? ""}`),
  initialPageParam: null,
  getNextPageParam: (lastPage) => lastPage.nextCursor, // null이면 끝
});

cursor 페이지네이션(4장)과 짝을 이룹니다. 응답의 nextCursor를 그대로 다음 요청에 넘깁니다.

Prefetch & select

  • prefetch: 마우스 호버·이동 직전에 queryClient.prefetchQuery로 미리 받아두면 체감 속도가 빨라집니다.
  • select: select: (data) => data.items처럼 필요한 부분만 뽑아 불필요한 리렌더를 줄입니다.

SSR 하이드레이션 (Next.js)

서버에서 미리 받아온 데이터를 클라이언트 캐시로 이어받는 패턴입니다. 첫 화면이 빠르고, 깜빡임이 없습니다.

서버: prefetchQuery → dehydrate(상태 직렬화) ↓ HTML과 함께 전달 ↓ 클라이언트: HydrationBoundary로 그 상태를 캐시에 주입 → 재요청 없이 즉시 표시

요청 취소 (AbortController)

queryFn은 signal을 받습니다. 검색어가 빠르게 바뀔 때 이전 요청을 취소해 race condition을 막습니다.

useQuery({
  queryKey: ["search", q],
  queryFn: ({ signal }) => api.get(`/search?q=${q}`, { signal }),
});

10. 동시성 & 아키텍처

Promise.all vs allSettled

메서드 동작 언제
Promise.all 하나라도 실패하면 전체 실패(fail-fast) 전부 성공해야 화면이 의미 있을 때
Promise.allSettled 각각의 성공/실패를 모두 받음 일부 실패해도 나머지는 보여줄 때(대시보드 위젯 등) 
const [user, orders] = await Promise.all([
  api.get("/me"),
  api.get("/orders"),
]); // 순차 호출보다 빠름 (병렬)

Race Condition

여러 비동기 요청의 응답 순서가 보장되지 않아 생기는 문제입니다. 검색 자동완성에서 "느린 옛 요청"이 "빠른 새 요청"보다 늦게 도착해 화면을 덮어쓰는 게 대표적입니다. 해결은 위의 AbortController 또는 React Query의 queryKey 변경입니다.

BFF (Backend For Frontend)

프론트가 여러 마이크로서비스를 직접 다 호출하면 복잡합니다. 화면에 맞춰 데이터를 모아주는 전용 서버 계층을 두는 패턴입니다.

프론트 → BFF → (user 서비스 + order 서비스 + product 서비스 fan-out) ↑ 화면에 딱 맞는 형태로 합쳐서 응답

API Gateway

모든 요청의 단일 진입점. 라우팅, 인증, rate limiting, 로깅을 한 곳에서 처리합니다. BFF와 달리 "공통 관문" 성격입니다.

11. 프론트가 알면 좋은 백엔드 내부

풀스택 협업에서 백엔드의 말을 알아듣고, "이 API가 왜 느린지"를 함께 짚기 위한 최소한의 내부 감각입니다.

N+1 문제

목록 1번 조회 후, 각 항목의 연관 데이터를 위해 N번 더 조회하는 비효율입니다. 목록 API가 유독 느리면 의심해볼 지점입니다.

// 글 10개 조회(1) + 각 글의 작성자 조회(10) = 11번 쿼리
// 해결: JOIN 또는 eager loading으로 한 번에
SELECT p.*, u.name
FROM posts p JOIN users u ON p.user_id = u.id;

트랜잭션과 ACID

"여러 작업을 하나로 묶어, 다 되거나 다 안 되게" 하는 것이 트랜잭션입니다. 계좌 이체에서 출금만 되고 입금이 실패하면 안 되는 것과 같습니다.

속성 의미
Atomicity 전부 성공 또는 전부 취소(원자성)
Consistency 규칙(제약)을 항상 만족
Isolation 동시 트랜잭션이 서로 간섭하지 않음
Durability 커밋되면 장애가 나도 보존

인덱스

책의 색인처럼, 특정 컬럼 조회를 빠르게 합니다. 읽기는 빨라지지만 쓰기·저장공간 비용이 듭니다. "이 검색 느린데 인덱스 있나요?"가 백엔드에 던질 수 있는 좋은 질문입니다.

프론트에서 볼 포인트

느린 API를 만났을 때 "느려요"가 아니라 "이 목록이 N+1 같고, 정렬 컬럼에 인덱스가 있는지 궁금합니다"처럼 말하면 협업의 질이 달라집니다.

12. 심화 체크리스트

  • □ HTTP/1.1, 2, 3의 차이와 멀티플렉싱을 설명할 수 있다.
  • □ Cache-Control과 ETag/304가 어떻게 트래픽을 줄이는지 안다.
  • □ Richardson 성숙도 모델로 API 수준을 가늠할 수 있다.
  • □ Idempotency Key가 왜 결제 API에 필요한지 안다.
  • □ cursor(keyset) 페이지네이션이 offset보다 나은 경우를 안다.
  • □ 일관된 에러 응답 구조(problem+json)를 읽고 화면에 매핑할 수 있다.
  • □ 429와 지수 백오프 재시도를 이해한다.
  • □ OAuth 2.0(인가)과 OIDC(인증)의 차이를 설명할 수 있다.
  • □ Authorization Code + PKCE 흐름을 안다.
  • □ Access/Refresh 분리와 Refresh Rotation의 이유를 안다.
  • □ 토큰 저장 위치별 보안 트레이드오프를 안다.
  • □ XSS와 CSRF의 차이와 각각의 방어를 안다.
  • □ CORS preflight가 언제 발생하는지 안다.
  • □ Polling, SSE, WebSocket을 상황에 맞게 고를 수 있다.
  • □ React Query의 optimistic update와 롤백을 구현할 수 있다.
  • □ infinite query와 cursor 페이지네이션을 연결할 수 있다.
  • □ SSR 하이드레이션의 흐름을 안다.
  • □ AbortController로 race condition을 막을 수 있다.
  • □ Promise.all과 allSettled를 구분해 쓴다.
  • □ BFF와 API Gateway의 역할 차이를 안다.
  • □ N+1, 트랜잭션, 인덱스의 개념을 백엔드와 대화할 수준으로 안다.
이 문서의 최종 목표

API를 호출하고 디버깅하는 것을 넘어, 설계 의도를 읽고 더 나은 방향을 제안하며, 백엔드와 같은 언어로 성능·보안·동시성을 논의할 수 있는 풀스택 감각의 프론트엔드 개발자가 되는 것입니다.
