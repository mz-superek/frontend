2. HTTP 통신 구조

HTTP는 브라우저와 서버가 데이터를 주고받는 규칙입니다.

브라우저 ↓ Request 서버 ↓ Response 브라우저

Request 구조

Method

무슨 행동을 할지 나타냅니다.

GET /users
POST /users
PATCH /users/123
DELETE /users/123

Header

요청의 부가 정보입니다.

Authorization: Bearer xxx
Content-Type: application/json
Accept: application/json
Header 의미
Authorization 인증 정보
Content-Type 보내는 데이터 타입
Accept 받고 싶은 데이터 타입
Cookie 브라우저가 서버에 보내는 쿠키
Cache-Control 캐시 정책

Body

서버에 전달하는 실제 데이터입니다. 주로 POST, PUT, PATCH에서 사용합니다.

{
  "name": "Kim",
  "email": "kim@test.com"
}

Response 구조

Response는 보통 상태 코드, 헤더, 바디로 구성됩니다.

HTTP/1.1 200 OK
Content-Type: application/json

{
  "success": true,
  "data": {
    "id": 1,
    "name": "Kim"
  }
}

3. HTTP Method

Method 의미 예시
GET 조회 GET /users/1
POST 생성 또는 복잡한 처리 요청 POST /users
PUT 전체 수정 PUT /users/1
PATCH 부분 수정 PATCH /users/1
DELETE 삭제 DELETE /users/1
왜 이 API는 POST인가?

POST /users는 사용자를 생성하기 때문입니다. 또 검색 조건이 너무 복잡해서 URL query로 표현하기 어렵다면 POST /users/search처럼 body를 사용하는 검색 API도 있을 수 있습니다.

Idempotent 개념

같은 요청을 여러 번 보내도 결과가 같으면 idempotent하다고 합니다.

Method 보통 idempotent? 설명
GET 예 여러 번 조회해도 데이터가 생성되지는 않음
POST 아니오 여러 번 보내면 여러 개 생성될 수 있음
PUT 예 같은 값으로 전체 교체
PATCH 상황에 따라 다름 부분 수정 방식에 따라 다름
DELETE 예 삭제 상태는 유지됨

4. 상태 코드

코드 의미 프론트에서 볼 포인트
200 성공 응답 데이터를 화면에 반영
201 생성 성공 생성 후 목록 갱신 또는 상세 이동
204 성공, 본문 없음 DELETE·일부 PUT의 응답. 응답이 비어 있어도 성공이니 당황하지 말 것
301 / 302 / 307 / 308 리다이렉트 요청이 다른 URL로 이동됨. HTTP→HTTPS, 경로 변경 등
400 잘못된 요청 필수값, 형식, request body 확인
422 검증 실패 형식은 맞지만 값이 규칙 위반. 요즘 백엔드는 400 대신 422로 주기도 함
401 인증 안 됨 토큰 없음, 만료, 로그인 필요
403 권한 없음 로그인은 됐지만 접근 권한 없음
404 대상 없음 URL, path parameter, 데이터 존재 여부 확인
409 충돌 이미 존재하는 리소스를 또 만들려 할 때 등 (예: 중복 가입)
429 요청 과다 짧은 시간에 너무 많이 호출. rate limit. 재시도 간격 두기
500 서버 오류 서버 로그 확인 요청, request 정보 공유
외우지 말고 앞자리로 기억하기

2xx는 성공, 3xx는 이동(리다이렉트), 4xx는 내 요청이 문제(필드·권한·URL), 5xx는 서버가 문제입니다. 4xx면 내 요청을 먼저 의심하고, 5xx면 백엔드에 로그 확인을 요청하세요.

5. REST API 설계 감각

REST에서 중요한 감각은 URL은 리소스, Method는 동작이라는 점입니다.

좋은 예

GET /users
GET /users/123
POST /users
PATCH /users/123
DELETE /users/123

좋지 않은 예

GET /getUser
POST /createUser

Path Parameter vs Query Parameter

구분 예시 용도
Path Parameter /users/123 특정 대상
Query Parameter /users?page=1&size=20 조회 조건, 페이지, 정렬

JSON 구조 읽기

{
  "data": {
    "id": 1,
    "name": "Kim"
  }
}
response.data.name

페이지네이션: offset vs cursor

목록 API는 보통 두 방식 중 하나로 페이지를 나눕니다.

방식 예시 특징
offset 기반 /users?page=1&size=20 페이지 번호로 이동. 1·2·3 페이지네이션 UI에 적합. 중간에 데이터가 추가·삭제되면 누락·중복 가능
cursor 기반 /users?cursor=eyJpZCI6MTAwfQ&size=20 "이 지점 다음부터"를 가리키는 커서로 이동. 무한 스크롤에 적합. 데이터가 바뀌어도 안정적
프론트에서 볼 포인트

응답에 total, page, hasNext, nextCursor 같은 값이 있는지 확인하세요. 무한 스크롤이라면 거의 cursor 방식이고, 응답으로 받은 nextCursor를 다음 요청에 그대로 넣으면 됩니다.

정렬 / 필터

정렬·필터 조건도 query parameter로 표현합니다.

GET /users?sort=createdAt,desc&status=active&keyword=kim

API 버저닝

API가 바뀌어도 기존 화면이 깨지지 않도록 URL에 버전을 둡니다.

GET /v1/users
GET /v2/users

/v1과 /v2는 응답 구조가 다를 수 있으니, 문서에서 지금 보고 있는 게 어느 버전인지부터 확인하세요.

Stoplight 문서 볼 때 체크할 것

  1. Method: GET인지 POST인지
  2. URL: path parameter가 있는지
  3. Header: Authorization이 필요한지
  4. Request Body: 어떤 값을 보내야 하는지
  5. Response: 화면에 사용할 값이 어디에 있는지
  6. Error Response: 실패 시 어떤 메시지가 오는지

6. 인증 / 인가

인증 Authentication

사용자가 누구인지 확인하는 것입니다. 예: 로그인, 토큰 검증

인가 Authorization

그 사용자가 무엇을 할 수 있는지 확인하는 것입니다. 예: 관리자 권한, 프로젝트 접근 권한

Session 방식

로그인 ↓ 서버가 Session 저장 ↓ 브라우저에 Cookie 발급 ↓ 브라우저가 Cookie 자동 전송

JWT 방식

로그인 ↓ 서버가 JWT 발급 ↓ 프론트가 토큰 저장 ↓ Authorization Header에 붙여 API 호출
Authorization: Bearer xxx.yyy.zzz

Cookie vs LocalStorage vs Header

구분 장점 주의점
LocalStorage 사용 쉬움 XSS에 취약할 수 있음
Cookie HttpOnly 설정 가능 CSRF 고려 필요
Authorization Header API 인증에 명확함 토큰 저장 위치를 별도로 결정해야 함
401 vs 403

401: 로그인 안 됨, 토큰 없음, 토큰 만료

403: 로그인은 됐지만 권한 없음

7. 데이터베이스 기초

RDB

관계형 데이터베이스입니다. 대표적으로 MySQL, PostgreSQL이 있습니다.

id name email
1 Kim kim@test.com

용어

  • Table: 데이터 묶음. 예: users
  • Column: 속성. 예: id, name, email
  • Row: 실제 데이터 1건

SQL 읽기

SELECT *
FROM users;
SELECT *
FROM users
WHERE id = 1;

프론트 관점에서 중요한 감각

  • API 응답이 어느 테이블/엔티티에서 오는지 이해하기
  • userId만 있고 userName이 없으면 추가 API가 필요할 수 있음을 알기
  • nullable 값이 화면에서 깨지지 않도록 처리하기
  • 목록 화면에서는 total count, page, size 값을 확인하기

8. 서버 환경 기초

환경변수

환경변수는 환경마다 달라지는 값이나 민감한 값을 코드와 분리하기 위해 사용합니다.

API_URL=https://api.company.com
DB_PASSWORD=secret
Next.js 전용 주의

NEXT_PUBLIC_이 붙은 환경변수는 브라우저에 노출됩니다. 비밀번호, secret key 같은 값은 절대 넣으면 안 됩니다.

환경 분리

환경 의미
Local 내 PC 개발 환경
Development 개발 서버
Staging QA, 검수 환경
Production 운영 환경

CORS

CORS는 브라우저가 서로 다른 Origin 간 요청을 제한하는 보안 정책입니다.

프론트: http://localhost:3000
API:    https://api.company.com

Origin이 다르기 때문에 서버가 허용 헤더를 내려줘야 합니다.

Access-Control-Allow-Origin: http://localhost:3000
Access-Control-Allow-Credentials: true

핵심: CORS는 프론트 코드 문제처럼 보이지만, 실제 해결은 보통 서버 설정에서 합니다.

9. 실무 API 디버깅 편

API 디버깅의 목표는 “안 돼요”가 아니라 “어디에서 실패했는지”를 좁히는 것입니다.

API 오류가 났을 때 기본 순서

  1. Network 탭에서 요청이 실제로 나갔는지 확인
  2. Request URL이 맞는지 확인
  3. Method가 문서와 같은지 확인
  4. Request Header에 Authorization이 있는지 확인
  5. Request Payload가 문서와 같은지 확인
  6. Status Code 확인
  7. Response Body의 에러 메시지 확인
  8. 환경변수의 API base URL 확인
좋은 질문 방식

“POST /users 호출 시 400이 발생합니다. Network 탭에서 request body는 아래와 같고, response message는 email is required입니다. 필드명이 문서와 다른지 확인 부탁드립니다.”

10. Network 탭 보는 법

Chrome DevTools의 Network 탭은 프론트 API 디버깅의 핵심 도구입니다.

1단계: 요청 찾기

  • DevTools 열기
  • Network 탭 선택
  • Fetch/XHR 필터 선택
  • 버튼 클릭 또는 화면 새로고침
  • API 요청 클릭

2단계: Headers 확인

항목 확인 내용
Request URL API 주소가 맞는가?
Request Method GET/POST/PATCH 등이 문서와 같은가?
Status Code 200, 400, 401, 403, 500 중 무엇인가?
Authorization Bearer token이 붙었는가?
Content-Type application/json인가?

3단계: Payload 확인

POST, PUT, PATCH 요청에서 내가 보낸 값이 맞는지 봅니다.

{
  "name": "Kim",
  "email": "kim@test.com"
}

4단계: Response 확인

서버가 내려준 성공 데이터 또는 에러 메시지를 확인합니다.

{
  "code": "INVALID_REQUEST",
  "message": "email is required"
}

상태 코드별 확인 포인트

상태 먼저 확인할 것
400 payload 필드명, 필수값, 타입
401 토큰 존재 여부, 만료 여부, Authorization Header
403 내 계정 권한, role, 프로젝트 접근 권한
404 URL 오타, path parameter, 서버 라우팅
500 서버 로그 확인 요청, 재현 request 전달
CORS 서버 CORS 설정, credentials 설정

11. Axios Interceptor

Interceptor는 모든 요청 또는 응답을 가로채서 공통 처리를 하는 기능입니다.

왜 필요한가?

  • 모든 API 요청에 토큰을 자동으로 붙이기
  • 401 발생 시 로그인 페이지로 보내기
  • 공통 에러 메시지 처리
  • API base URL을 한 곳에서 관리

기본 예시

import axios from "axios";

export const api = axios.create({
  baseURL: import.meta.env.VITE_API_URL,
  timeout: 10000,
});

api.interceptors.request.use((config) => {
  const token = localStorage.getItem("accessToken");

  if (token) {
    config.headers.Authorization = `Bearer ${token}`;
  }

  return config;
});

api.interceptors.response.use(
  (response) => response,
  (error) => {
    if (error.response?.status === 401) {
      // 토큰 만료 또는 로그인 필요
      localStorage.removeItem("accessToken");
      window.location.href = "/login";
    }

    return Promise.reject(error);
  }
);
프레임워크별 환경변수 예시
  • Vite: import.meta.env.VITE_API_URL
  • Next.js: process.env.NEXT_PUBLIC_API_URL
  • Create React App: process.env.REACT_APP_API_URL

토큰 재발급 흐름

API 호출 ↓ 401 발생 ↓ Refresh Token으로 Access Token 재발급 요청 ↓ 새 Access Token 저장 ↓ 실패했던 요청 재시도 ↓ 재발급도 실패하면 로그아웃

실무에서는 동시 요청이 여러 개일 때 refresh 요청이 중복되지 않도록 큐 처리나 lock 처리가 필요할 수 있습니다.

12. React Query

React Query는 서버 상태를 관리하는 라이브러리입니다. API 호출 결과, 로딩, 에러, 캐시, 재요청을 편하게 다룰 수 있습니다.

클라이언트 상태 vs 서버 상태

구분 예시 관리 도구
클라이언트 상태 모달 열림, 탭 선택 useState, Zustand 등
서버 상태 사용자 목록, 프로젝트 상세 React Query

조회 useQuery

import { useQuery } from "@tanstack/react-query";
import { api } from "./api";

function useUsers() {
  return useQuery({
    queryKey: ["users"],
    queryFn: async () => {
      const response = await api.get("/users");
      return response.data;
    },
  });
}

생성/수정/삭제 useMutation

import { useMutation, useQueryClient } from "@tanstack/react-query";

function useCreateUser() {
  const queryClient = useQueryClient();

  return useMutation({
    mutationFn: async (body) => {
      const response = await api.post("/users", body);
      return response.data;
    },
    onSuccess: () => {
      queryClient.invalidateQueries({ queryKey: ["users"] });
    },
  });
}

React Query 디버깅 포인트

  • queryKey가 올바른가?
  • 파라미터가 바뀔 때 queryKey도 바뀌는가?
  • enabled 조건 때문에 호출이 막힌 것은 아닌가?
  • mutation 성공 후 invalidateQueries를 했는가?
  • 캐시 때문에 이전 데이터가 보이는 것은 아닌가?

enabled 예시

useQuery({
  queryKey: ["user", userId],
  queryFn: () => api.get(`/users/${userId}`),
  enabled: !!userId,
});

이 코드는 userId가 있을 때만 API를 호출합니다.

staleTime vs gcTime (캐시의 핵심)

"왜 재요청이 되는지 / 안 되는지"는 대부분 이 두 값으로 결정됩니다.

옵션 의미
staleTime 데이터를 "신선하다"고 보는 시간. 이 시간 안에는 같은 데이터를 다시 봐도 재요청하지 않고 캐시를 씁니다. 기본값 0 (= 항상 stale).
gcTime 화면에서 안 쓰이게 된 캐시를 메모리에 보관하는 시간. 이 시간이 지나면 캐시를 버립니다. 기본값 5분. (v4의 cacheTime이 이름만 바뀐 것) 
useQuery({
  queryKey: ["users"],
  queryFn: fetchUsers,
  staleTime: 1000 * 60, // 1분 동안은 재요청하지 않음
});

Optimistic Update (낙관적 업데이트)

서버 응답을 기다리지 않고 화면을 먼저 바꿔 빠른 UX를 주는 방식입니다. 실패하면 이전 상태로 되돌립니다(rollback).

useMutation({
  mutationFn: toggleLike,
  onMutate: async (next) => {
    await queryClient.cancelQueries({ queryKey: ["post", id] });
    const prev = queryClient.getQueryData(["post", id]);
    queryClient.setQueryData(["post", id], next); // 먼저 화면에 반영
    return { prev };
  },
  onError: (err, next, context) => {
    queryClient.setQueryData(["post", id], context.prev); // 실패하면 롤백
  },
  onSettled: () => {
    queryClient.invalidateQueries({ queryKey: ["post", id] });
  },
});
v5 명칭 변화

TanStack Query v5에서 useMutation의 isLoading이 isPending으로 바뀌었고, useQuery의 status 값도 loading → pending으로 바뀌었습니다. v4 코드를 보다가 헷갈리면 이 부분을 확인하세요.

13. 인증 흐름 추적

인증 오류는 프론트에서 자주 만나는 문제입니다. 흐름을 순서대로 보면 원인을 좁히기 쉽습니다.

로그인 성공 흐름

로그인 폼 제출 ↓ POST /login ↓ accessToken / refreshToken 수신 ↓ 토큰 저장 ↓ 이후 API 요청에 Authorization Header 추가 ↓ 보호된 API 호출 성공

401 발생 시 확인

  1. 로그인 응답에 토큰이 왔는가?
  2. 토큰을 저장했는가?
  3. API 요청 Header에 토큰이 붙었는가?
  4. Bearer 형식이 맞는가?
  5. 토큰이 만료되었는가?
  6. 서버가 기대하는 인증 방식이 Cookie인지 Header인지 확인했는가?

403 발생 시 확인

  1. 로그인은 되어 있는가?
  2. 현재 계정 role이 무엇인가?
  3. 이 API가 관리자 권한을 요구하는가?
  4. 특정 프로젝트/조직 권한이 필요한가?
  5. 백엔드에서 권한 매핑이 누락된 것은 아닌가?

Cookie 인증에서 확인할 것

항목 설명
withCredentials cross-origin 요청에 cookie를 보낼 때 필요
SameSite cross-site cookie 전송 정책
Secure HTTPS에서만 cookie 전송
HttpOnly JS에서 cookie 접근 불가
Domain / Path cookie가 적용되는 범위

Axios Cookie 예시

const api = axios.create({
  baseURL: import.meta.env.VITE_API_URL,
  withCredentials: true,
});
주의

Cookie 기반 인증에서는 프론트의 withCredentials: true와 서버의 Access-Control-Allow-Credentials: true 설정이 함께 맞아야 합니다.

14. 실무 상황별 빠른 판단표

상황 가능성 높은 원인 확인할 곳
API 호출 자체가 안 보임 이벤트 미연결, 조건부 호출 막힘 Console, React Query enabled
400 요청 데이터 문제 Payload, API 문서
401 인증 문제 Authorization Header, Cookie
403 권한 문제 계정 role, 프로젝트 권한
404 URL 문제 Request URL, path parameter
500 서버 문제 가능성 Response message, 백엔드 로그
CORS 서버 허용 설정 문제 Response Header, 서버 CORS 설정
화면 데이터가 안 바뀜 캐시 갱신 누락 React Query invalidateQueries

15. 최종 체크리스트

  • □ 왜 이 API가 POST인지 설명할 수 있다.
  • □ GET, POST, PUT, PATCH, DELETE 차이를 안다.
  • □ 200, 201, 204, 400, 401, 403, 404, 422, 429, 500의 의미를 안다.
  • □ Path Parameter와 Query Parameter를 구분할 수 있다.
  • □ offset과 cursor 페이지네이션의 차이를 안다.
  • □ API 버저닝(/v1, /v2)이 왜 필요한지 안다.
  • □ Stoplight 문서에서 request/response 구조를 읽을 수 있다.
  • □ Authorization Header에 토큰을 붙이는 흐름을 이해한다.
  • □ 401과 403을 구분할 수 있다.
  • □ Cookie, LocalStorage, Header 인증의 차이를 안다.
  • □ Network 탭에서 Headers, Payload, Response를 확인할 수 있다.
  • □ Axios Interceptor가 왜 필요한지 설명할 수 있다.
  • □ React Query의 useQuery/useMutation 차이를 안다.
  • □ staleTime과 gcTime이 캐시 동작에 어떤 영향을 주는지 안다.
  • □ CORS가 왜 발생하고 보통 누가 해결하는지 안다.
  • □ 환경변수가 왜 필요한지 안다.
  • □ 백엔드가 “테이블”, “컬럼”, “JOIN”이라고 말했을 때 대략 이해할 수 있다.
이 문서의 최종 목표

API 문서를 보고 기능을 구현하는 것에서 끝나지 않고, 인증 만료, 권한 오류, 환경 차이, 응답 구조 불일치가 생겼을 때 원인을 좁혀갈 수 있는 프론트엔드 개발자가 되는 것입니다.
