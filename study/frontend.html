2. 브라우저가 화면을 그리는 과정

코드 한 줄이 화면 픽셀이 되기까지의 흐름(Critical Rendering Path)을 알면 "왜 느린지", "왜 깜빡이는지"가 보입니다.

HTML 파싱 → DOM CSS 파싱 → CSSOM DOM + CSSOM → Render Tree ↓ Layout(요소 위치·크기 계산) ↓ Paint(색·텍스트 등 픽셀화) ↓ Composite(레이어 합성)
단계 설명
DOM HTML을 트리 구조의 객체로 변환
CSSOM CSS를 스타일 규칙 트리로 변환
Render Tree 화면에 보이는 요소 + 스타일을 결합 (display:none은 제외)
Layout(Reflow) 각 요소의 위치·크기 계산. 가장 비용이 큼
Paint(Repaint) 색, 그림자, 텍스트 등을 칠함
왜 알아야 하나

width, top 같은 속성을 바꾸면 Layout부터 다시(reflow) 일어나 무겁고, transform, opacity는 Composite 단계만 거쳐 가볍습니다. 애니메이션을 transform으로 하라는 조언이 여기서 나옵니다. (자세한 최적화는 심화편)

3. 시맨틱 HTML & 접근성

마크업의 "의미"는 SEO, 접근성, 유지보수를 동시에 좌우합니다. div만으로도 화면은 나오지만, 의미가 없으면 보조기기와 검색엔진이 구조를 이해하지 못합니다.

시맨틱 태그

태그 의미
header / nav / main / footer 페이지의 큰 영역 구분
article / section 독립 콘텐츠 / 주제 단위 묶음
button / a 동작은 button, 이동은 a. 역할에 맞게
h1~h6 문서의 제목 위계. 건너뛰지 않기

접근성(a11y) 기본기

  • 이미지에는 의미를 담은 alt. 장식용이면 빈 alt=""
  • 폼 입력은 label과 연결 (for / id)
  • 색만으로 정보를 전달하지 않기 (색약 고려)
  • 키보드만으로 모든 기능 사용 가능해야 함
  • 네이티브 요소로 안 될 때만 role, aria-* 보강
핵심 원칙

"ARIA를 쓰는 것보다 시맨틱 네이티브 요소를 쓰는 게 낫다." div에 클릭 핸들러를 다는 대신 button을 쓰면 포커스·키보드·스크린리더가 공짜로 따라옵니다. (WCAG 기준 심화는 심화편)

4. CSS 핵심

박스 모델

모든 요소는 content → padding → border → margin의 상자입니다. box-sizing: border-box를 쓰면 width에 padding·border가 포함돼 계산이 직관적입니다.

레이아웃: Flexbox vs Grid

도구 적합한 경우
Flexbox 한 방향(행 또는 열) 정렬. 내비게이션, 버튼 그룹
Grid 2차원(행과 열) 레이아웃. 카드 갤러리, 페이지 골격

우선순위(Specificity)

같은 요소에 여러 규칙이 충돌하면 점수가 높은 게 이깁니다.

인라인 스타일 > id > class · 속성 · 가상클래스 > 요소 · 가상요소
주의

!important는 우선순위를 강제로 덮어쓰지만, 남용하면 이후 수정이 지옥이 됩니다. 선택자 구조로 푸는 게 우선입니다.

반응형

/* 모바일 우선 후 확장 */
.card { padding: 12px; }
@media (min-width: 768px) {
  .card { padding: 24px; }
}

단위는 고정값 px, 상대값 rem/em/%, 뷰포트 vw/vh를 상황에 맞게 씁니다. 폰트·여백은 보통 rem이 접근성에 유리합니다.

5. JavaScript 핵심

변수와 스코프

let/const는 블록 스코프이고 재선언이 안 됩니다. var는 함수 스코프라 예측이 어려워 지금은 거의 안 씁니다. 값이 안 바뀌면 기본적으로 const.

클로저

함수가 선언될 때의 바깥 변수를 기억하는 성질입니다. React의 상태 관리, 이벤트 핸들러가 이 위에서 돕니다.

function counter() {
  let count = 0;
  return () => ++count; // 바깥 count를 계속 기억
}
const next = counter();
next(); // 1
next(); // 2

비동기와 이벤트 루프

JS는 한 번에 하나만 처리하지만(싱글 스레드), 오래 걸리는 작업은 비동기로 넘기고 끝나면 큐에서 꺼내 실행합니다.

콜 스택 비워짐 ↓ 마이크로태스크 큐(Promise) 먼저 처리 ↓ 매크로태스크 큐(setTimeout 등) 처리
// 콜백 → Promise → async/await 로 진화
const res = await fetch("/api/users");
const data = await res.json();

자주 쓰는 배열 메서드

map(변환), filter(거르기), reduce(누적), find(하나 찾기). React 목록 렌더링은 거의 map입니다.

6. DOM & 이벤트

DOM은 HTML의 객체 표현이고, JS로 이를 읽고 바꿉니다. React를 쓰면 직접 만질 일은 줄지만 원리는 알아야 합니다.

이벤트 버블링과 위임

이벤트는 자식에서 부모로 전파됩니다(버블링). 이를 이용해 부모 하나에만 리스너를 달아 여러 자식을 처리하는 게 "이벤트 위임"입니다.

list.addEventListener("click", (e) => {
  const item = e.target.closest("li");
  if (item) select(item.dataset.id);
}); // li마다 리스너를 달지 않아도 됨
프레임워크와의 연결

React의 onClick은 내부적으로 이벤트 위임으로 동작합니다. 버블링·캡처링을 이해하면 모달 바깥 클릭 닫기, 드롭다운 같은 UI를 정확히 만들 수 있습니다.

7. 프레임워크와 컴포넌트 사고

React·Vue 같은 프레임워크의 공통 아이디어는 두 가지입니다.

개념 의미
선언형 UI "DOM을 이렇게 바꿔라"가 아니라 "상태가 이러면 화면은 이렇다"를 선언. 프레임워크가 차이를 계산해 반영
컴포넌트 화면을 재사용 가능한 조각으로 나눔. 각 조각은 자기 데이터(props/state)와 UI를 가짐
퍼블리싱 경험과의 연결

잘 나눈 컴포넌트는 의미 있는 마크업 구조와 닮아 있습니다. 시맨틱하게 영역을 나누던 감각이 그대로 컴포넌트 분리 감각으로 이어집니다.

8. React 기초

JSX

JS 안에서 HTML 비슷한 문법으로 UI를 표현합니다. class 대신 className, 표현식은 {}로 감쌉니다.

function Hello({ name }) {
  return <h1 className="title">안녕, {name}</h1>;
}

props와 state

구분 설명
props 부모가 자식에게 내려주는 값. 자식은 읽기만 (변경 불가)
state 컴포넌트가 스스로 가진 변하는 값. 바뀌면 화면이 다시 그려짐 
import { useState } from "react";

function Counter() {
  const [count, setCount] = useState(0);
  return (
    <button onClick={() => setCount(count + 1)}>
      {count}
    </button>
  );
}

렌더링과 key

state나 props가 바뀌면 컴포넌트가 다시 실행되어 새 화면을 만듭니다. 목록을 그릴 때는 각 항목에 고유한 key가 필요합니다(인덱스 말고 안정적인 id).

{users.map((u) => (
  <li key={u.id}>{u.name}</li>
))}
흔한 실수

state를 직접 바꾸면(count++) 화면이 안 바뀝니다. 반드시 setCount 같은 setter로 바꿔야 React가 변화를 감지합니다.

9. 상태의 3가지 종류

"상태 관리가 어렵다"는 보통 종류를 안 나눠서 생깁니다. 먼저 어떤 상태인지부터 구분하세요.

종류 예시 도구
로컬 UI 상태 모달 열림, 입력값, 탭 선택 useState, useReducer
전역 클라이언트 상태 로그인 사용자, 테마, 언어 Context, Zustand, Redux
서버 상태 사용자 목록, 상세 데이터 React Query (TanStack Query)
가장 중요한 구분

서버에서 온 데이터(서버 상태)를 전역 스토어에 직접 넣어 관리하면 캐시·동기화가 지옥이 됩니다. 서버 상태는 React Query에 맡기고, 전역 스토어에는 진짜 클라이언트 상태만 두세요. (API 연동 자세히는 백엔드 기초편 참고)

10. 렌더링 방식과 라우팅

같은 React 앱도 "어디서 HTML을 만드느냐"에 따라 성격이 달라집니다.

방식 HTML 생성 위치 특징
CSR 브라우저(JS 실행 후) 초기 로딩 느릴 수 있음, 이후 빠름. 일반 SPA
SSR 요청 시 서버 첫 화면·SEO 유리. 매 요청 서버 작업
SSG 빌드 시 미리 가장 빠름. 자주 안 바뀌는 페이지(문서·블로그)

Next.js는 이 방식들을 페이지·컴포넌트 단위로 섞어 쓸 수 있게 해줍니다. SPA 라우팅은 페이지 전체를 새로 받지 않고, JS가 URL에 맞는 컴포넌트만 바꿔 그립니다.

11. 빌드 · 번들 · 패키지

브라우저는 우리가 쓰는 최신 문법·여러 파일·TS를 그대로 못 읽습니다. 빌드 도구가 이를 변환·결합해줍니다.

도구/개념 역할
번들러 (Vite, webpack) 여러 모듈을 묶고 최적화. 개발 서버 제공
트랜스파일 (Babel, SWC) 최신 JS·JSX·TS를 브라우저용으로 변환
패키지 매니저 (npm, pnpm) 라이브러리 설치·버전 관리 
// 모듈 시스템: 파일 간에 코드를 나눠 쓰기
export function add(a, b) { return a + b; } // utils.js
import { add } from "./utils.js";          // 다른 파일에서
알아두면 좋은 것

package.json의 dependencies(실행에 필요)와 devDependencies(개발에만 필요) 구분, scripts의 dev/build 명령 정도는 읽을 수 있어야 합니다.

12. 개발자 도구로 디버깅

Chrome DevTools는 프론트 디버깅의 기본기입니다.

패널 쓰임
Elements DOM·적용된 CSS 확인·실시간 수정
Console 로그·에러 확인, JS 즉석 실행
Network API 요청/응답·상태 코드·헤더 (백엔드편 참고)
Sources 중단점(breakpoint) 걸어 코드 흐름 추적
좋은 디버깅 습관

"안 돼요" 대신 "Elements에서 이 요소에 이 클래스가 안 붙고, Console에 이런 에러가 있습니다"처럼 어디서 끊겼는지를 좁혀가는 것이 핵심입니다.

13. 기초 체크리스트

  • □ HTML→DOM, CSS→CSSOM, Layout, Paint의 흐름을 설명할 수 있다.
  • □ transform/opacity가 width/top보다 가벼운 이유를 안다.
  • □ 상황에 맞는 시맨틱 태그를 고를 수 있다.
  • □ alt, label, 키보드 접근성의 기본을 지킨다.
  • □ box-sizing, Flexbox, Grid를 구분해 쓴다.
  • □ CSS 우선순위와 !important의 위험을 안다.
  • □ let/const/var와 스코프를 안다.
  • □ 클로저가 무엇인지 예로 설명할 수 있다.
  • □ 이벤트 루프와 async/await의 동작을 안다.
  • □ map/filter/reduce를 적절히 쓴다.
  • □ 이벤트 버블링과 위임을 이해한다.
  • □ 선언형 UI와 컴포넌트 사고를 설명할 수 있다.
  • □ props와 state의 차이를 안다.
  • □ state는 setter로만 바꿔야 함을 안다.
  • □ 목록 렌더링에서 key의 역할을 안다.
  • □ 로컬/전역/서버 상태를 구분한다.
  • □ CSR/SSR/SSG의 차이를 안다.
  • □ 번들러·트랜스파일·패키지 매니저의 역할을 안다.
  • □ DevTools의 Elements/Console/Network/Sources를 쓸 수 있다.
이 문서의 최종 목표

화면을 만드는 것을 넘어, 브라우저의 동작을 이해하고 의미 있는 마크업과 유지보수 가능한 컴포넌트를 작성하며, 문제가 생겼을 때 어디서 끊겼는지 좁혀갈 수 있는 프론트엔드 개발자가 되는 것입니다. 더 깊은 렌더링 내부·성능· 최적화·테스트는 심화편에서 다룹니다.

맨 위로
