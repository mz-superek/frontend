2026-08-06 (목) · TanStack Query — 서버 상태는 "내 것"이 아니다: staleTime과 캐싱

프론트 심화

핵심 개념

useState에 담는 값은 내 앱이 소유한 "클라이언트 상태"지만, API로 받아온 데이터는 서버가 원본을 가진 서버 상태라서 받는 순간부터 낡기 시작한다(stale). TanStack Query(구 React Query)는 이 서버 상태를 queryKey 기준으로 캐시에 저장하고, staleTime 동안은 "신선(fresh)"으로 보고 재요청 없이 캐시를 쓰다가, 시간이 지나면 stale로 표시한 뒤 창 포커스·재마운트 같은 신호가 오면 백그라운드에서 조용히 다시 받아온다. 퍼블리싱으로 비유하면 캐시는 미리 뽑아둔 출력 시안 — 즉시 보여줄 수 있지만 원본 PSD(서버)가 바뀌었을 수 있으니 주기적으로 다시 뽑아야(refetch) 한다. useEffect+useState로 직접 fetch를 짜면 낡음 관리·중복 요청 제거·로딩/에러 처리를 전부 손으로 해야 하는데, 그걸 대신해주는 게 핵심이다.

import { useQuery } from '@tanstack/react-query';

function ProjectList({ teamId }: { teamId: string }) {
  const { data, isPending, isError } = useQuery({
    queryKey: ['projects', teamId], // 캐시 식별자 — teamId가 바뀌면 별도 캐시
    queryFn: () => fetch(`/api/teams/${teamId}/projects`).then(r => r.json()),
    staleTime: 60_000, // 1분간 '신선' — 재마운트해도 재요청 안 함
  });

  if (isPending) return <Spinner />;
  if (isError) return <ErrorBox />;
  return <ul>{data.map(p => <li key={p.id}>{p.name}</li>)}</ul>;
}

왜 알아야 하나

실무 React/Next.js의 데이터 페칭 표준이라 코드 리뷰에서 반드시 만나고, "왜 화면 전환할 때마다 API를 다시 쏘지?" 같은 이슈의 답이 대부분 staleTime/queryKey 설정에 있다.

오늘의 퀴즈

Q1. staleTime: 60_000으로 설정한 쿼리가 있다. 데이터를 받아온 지 30초 뒤, 같은 queryKey를 쓰는 컴포넌트가 다시 마운트되면?
① 무조건 서버에 재요청한다 ② 캐시를 즉시 보여주고 재요청은 하지 않는다 ③ 캐시를 보여주면서 백그라운드로 재요청한다 ④ 빈 화면에서 로딩부터 시작한다

Q2. 아래 코드의 문제점 하나를 찾아보자.

const { data } = useQuery({
  queryKey: ['projects'],
  queryFn: () => fetch(`/api/teams/${teamId}/projects`).then(r => r.json()),
});
정답·해설 보기

Q1 정답: ② — 받아온 지 30초면 아직 staleTime(1분) 안이라 fresh 상태. fresh인 동안은 재마운트·포커스가 와도 캐시만 쓰고 재요청하지 않는다. 1분이 지나 stale이 된 뒤라면 ③처럼 캐시를 먼저 보여주고 백그라운드에서 refetch한다.
Q2 정답: queryKey에 teamId가 빠졌다 — queryFn은 teamId를 쓰는데 키가 ['projects']로 고정이라, teamId가 바뀌어도 캐시 키가 같아서 이전 팀 데이터를 그대로 보여주고 재요청도 안 한다. 쿼리가 의존하는 값은 전부 키에 넣어야 한다(useEffect 의존성 배열과 같은 원리).

2026-08-05 (수) · Core Web Vitals — LCP·INP·CLS, 구글이 매기는 우리 페이지 성적표

프론트 심화

핵심 개념

Core Web Vitals는 구글이 "실제 사용자가 느끼는 페이지 품질"을 수치화한 3가지 지표다. LCP(Largest Contentful Paint)는 화면에서 가장 큰 콘텐츠(보통 히어로 이미지·제목)가 뜨기까지 걸린 시간, CLS(Cumulative Layout Shift)는 로딩 중 레이아웃이 덜컹 밀리는 정도, INP(Interaction to Next Paint)는 클릭·입력 후 화면이 반응하기까지의 지연이다. 퍼블리싱으로 비유하면 LCP는 "메인 비주얼이 몇 초 만에 보이나", CLS는 "이미지에 width/height 안 넣어서 본문이 밀려 내려가나", INP는 "버튼 눌렀는데 굳어 있나"를 재는 것. 기준은 LCP 2.5초 · CLS 0.1 · INP 200ms 이하가 "좋음"이고, 검색 순위에도 반영된다. 최근 공부한 코드 스플리팅(7/30)·메모이제이션(7/28)·useTransition(7/21)이 전부 이 지표를 좋게 만드는 "수단"이었다고 보면 된다.

// npm i web-vitals — 실제 사용자 환경에서 측정
import { onLCP, onCLS, onINP } from 'web-vitals';

onLCP(console.log);  // 최대 콘텐츠 표시 시간
onCLS(console.log);  // 레이아웃 밀림 누적 점수
onINP(console.log);  // 상호작용 반응 지연

/* CLS 예방은 사실 퍼블리셔의 오랜 습관 그대로 */
img { width: 100%; aspect-ratio: 16 / 9; } /* 자리 미리 확보 */

왜 알아야 하나

"성능 개선해주세요"라는 요청은 사실 "이 세 숫자를 낮춰주세요"라는 뜻인 경우가 대부분이다. Lighthouse·Search Console에서 이 지표로 진단하고, 어떤 무기(스플리팅? memo? 이미지 최적화?)를 꺼낼지 정하는 게 실무 성능 작업의 순서다.

2026-08-04 (화) · 트랜잭션과 ACID — "전부 성공 아니면 전부 취소"

클라우드·백엔드 기초

핵심 개념

서버에서 DB를 다루다 보면 "여러 쓰기 작업이 반드시 함께 성공해야 하는" 순간이 온다. 포인트 이체가 대표적 — A에서 차감 + B에 적립, 둘 중 하나만 실행되면 데이터가 깨진다. 트랜잭션은 이런 작업들을 하나의 묶음으로 묶어 전부 성공하면 반영(커밋), 하나라도 실패하면 전부 취소(롤백)하는 장치다. 퍼블리싱 시절 FTP로 파일 여러 개를 올리다 절반만 올라가서 사이트가 깨져 보이던 상황을 떠올리면 된다 — 트랜잭션은 그 "절반만 반영된 상태"가 아예 존재할 수 없게 만든다. 이 성질을 정리한 말이 ACID: 원자성(Atomicity, 전부 아니면 전무) · 일관성(Consistency, 규칙 위반 상태 금지) · 격리성(Isolation, 진행 중인 중간 상태를 다른 요청이 못 봄) · 지속성(Durability, 커밋된 건 장애가 나도 남음).

// Next.js Server Action + Prisma
'use server';
export async function transferPoints(fromId: string, toId: string, amount: number) {
  await prisma.$transaction(async (tx) => {
    await tx.user.update({ where: { id: fromId }, data: { points: { decrement: amount } } });
    await tx.user.update({ where: { id: toId },   data: { points: { increment: amount } } });
  }); // 안에서 하나라도 throw되면 둘 다 롤백
}

왜 알아야 하나

Server Action이나 API 라우트에서 두 테이블 이상을 함께 수정하는 순간 트랜잭션이 필요해진다. "저장은 됐는데 데이터가 반쯤 이상하다"는 버그의 상당수가 트랜잭션 없는 다중 쓰기에서 나온다. 지난 7/24의 인덱스가 "읽기"의 기본기였다면, 트랜잭션은 "쓰기"의 기본기.

2026-07-30 (목) · 코드 스플리팅 — React.lazy와 next/dynamic으로 첫 로딩 가볍게

프론트 심화

핵심 개념

번들러는 우리가 쓴 컴포넌트와 라이브러리를 JS 파일 묶음(번들)으로 만드는데, 그대로 두면 사용자가 첫 화면에서 안 쓰는 코드까지 전부 내려받게 된다. 퍼블리싱 시절 모든 페이지의 스타일을 style.css 하나에 몰아넣으면 어느 페이지를 열어도 전체를 내려받아야 했던 것과 같은 문제다. 코드 스플리팅은 이 번들을 쪼개서 지금 필요한 조각만 받게 하는 기법. React.lazy(() => import('./Heavy'))로 감싸면 그 컴포넌트 코드는 실제 렌더링 시점에 네트워크로 가져오고, 로딩 중 UI는 <Suspense fallback>이 담당한다. Next.js는 라우트(페이지) 단위로는 자동으로 쪼개주므로, 직접 손댈 일은 주로 "한 페이지 안의 무거운 컴포넌트"(차트·에디터·지도 등)이고 이때 next/dynamic을 쓴다.

import dynamic from 'next/dynamic';

// 반드시 모듈 최상위에서 선언 (컴포넌트 함수 안 ❌)
const HeavyChart = dynamic(() => import('@/widgets/heavy-chart'), {
  loading: () => <Skeleton className="h-64" />,
  ssr: false, // window 등 브라우저 API에 의존하는 라이브러리일 때
});

export function ReportPage() {
  const [open, setOpen] = useState(false);
  return (
    <>
      <Button onClick={() => setOpen(true)}>차트 보기</Button>
      {open && <HeavyChart />} {/* 버튼을 눌러야 비로소 다운로드 */}
    </>
  );
}

왜 알아야 하나

차트·에디터 라이브러리 하나가 수백 KB를 차지하는 일이 흔해서, 조건부로만 쓰이는 무거운 컴포넌트를 dynamic으로 빼는 건 초기 로딩(LCP·TTI) 개선의 가성비 좋은 첫 수다. React Compiler가 "렌더링 낭비"를 줄인다면, 코드 스플리팅은 "다운로드 낭비"를 줄이는 짝꿍 기법.

프론트 심화

핵심 개념

React는 부모가 리렌더링되면 props가 바뀌었든 말든 자식도 기본적으로 전부 다시 렌더링한다. memo(Component)는 "props가 그대로면 이 컴포넌트는 건너뛰어"라는 계약이다. 함정은 props 비교가 얕은 비교(Object.is, 참조만 비교)라는 것 — 렌더링마다 새로 만들어지는 객체·배열·함수는 내용이 같아도 "다른 값"으로 판정된다. 그래서 memo와 세트로, 계산된 값을 캐싱하는 useMemo(메모이제이션 — 의존성이 안 바뀌면 이전 값 재사용)와 함수를 캐싱하는 useCallback이 필요하다. 퍼블리싱 비유: 인쇄소와 "내용 안 바뀐 페이지는 다시 안 찍는다"고 계약(memo)해도, 매번 파일명을 바꿔 새 파일로 보내면(매 렌더마다 새 객체/함수) 인쇄소는 전부 새 페이지로 취급한다. 단, 대부분의 컴포넌트는 리렌더링이 충분히 싸므로 "측정해 보니 느린 곳"에만 거는 게 원칙이며, React Compiler가 이 수동 최적화를 자동화하는 방향으로 가고 있다. 

const Child = memo(function Child({ items, onSelect }: Props) {
  /* 무거운 렌더링 */
});

function Parent({ data }: { data: Item[] }) {
  const [query, setQuery] = useState('');

  // ❌ 매 렌더마다 새 배열·새 함수 생성 → memo 무력화
  // const items = data.filter(d => d.name.includes(query));
  // const onSelect = (id: string) => setSelected(id);

  // ✅ 의존성이 그대로면 이전 참조를 재사용 → memo가 작동
  const items = useMemo(
    () => data.filter(d => d.name.includes(query)),
    [data, query]
  );
  const onSelect = useCallback((id: string) => setSelected(id), []);

  return <Child items={items} onSelect={onSelect} />;
}

// 참고: useCallback(fn, deps) === useMemo(() => fn, deps)

핵심 개념

어제 본 useTransition이 "업데이트를 만드는 쪽"에서 급함/안 급함을 나눴다면, useDeferredValue는 "값을 받는 쪽"에서 뒤처진 값을 쓰는 훅이다. const deferredQuery = useDeferredValue(query)라고 하면, query가 바뀌는 순간에도 deferredQuery는 잠시 이전 값을 유지하다가, 급한 렌더링이 끝난 뒤 여유가 생기면 새 값으로 따라온다. 퍼블리싱 비유로는 라이브 미리보기 에디터: 타이핑(입력창)은 즉시 반영하되, 무거운 미리보기 화면은 타이핑이 잠잠해진 뒤 최신 상태로 갱신하는 것과 같다. 핵심 차이는 setState 호출부를 감쌀 수 없는 상황 — 값이 props로 내려와서 startTransition을 쓸 수 없을 때 — 에도 쓸 수 있다는 점이다. 

function SearchPage() {
  const [query, setQuery] = useState('');
  const deferredQuery = useDeferredValue(query);
  const isStale = query !== deferredQuery; // 아직 옛날 값을 보여주는 중인지

  return (
    <>
      <input value={query} onChange={(e) => setQuery(e.target.value)} />
      <div style={{ opacity: isStale ? 0.5 : 1 }}>
        <HeavyList query={deferredQuery} />
      </div>
    </>
  );
}

// ⚠️ 핵심: HeavyList는 반드시 memo로 감싸야 효과가 있다
const HeavyList = memo(function HeavyList({ query }: { query: string }) {
  const items = heavyFilter(query); // 무거운 연산
  return <ul>{items.map(...)}</ul>;

React 18부터 상태 업데이트에 우선순위를 매길 수 있게 됐는데, startTransition(() => { ... }) 안에서 실행한 업데이트는 "급하지 않음(transition)"으로 표시된다. 퍼블리싱 시절로 비유하면, 클라이언트가 "로고 수정(급함)"과 "전체 페이지 리뉴얼(중요하지만 급하진 않음)"을 동시에 요청했을 때 로고부터 먼저 처리하는 것과 같다. 급한 업데이트(키 입력, 클릭 반응)가 들어오면 React는 진행 중이던 transition 렌더링을 중단하고 급한 것부터 그린다. 함께 반환되는 isPending으로 "아직 그리는 중" 상태를 UI에 표시할 수 있다. 

const [query, setQuery] = useState('');
const [results, setResults] = useState<Item[]>([]);
const [isPending, startTransition] = useTransition();

function handleChange(e: React.ChangeEvent<HTMLInputElement>) {
  const next = e.target.value;
  setQuery(next);                    // 급함: 입력창은 즉시 반영
  startTransition(() => {
    setResults(heavyFilter(next));   // 안 급함: 무거운 목록 갱신은 뒤로
  });
}

return (
  <>
    <input value={query} onChange={handleChange} />
    <div style={{ opacity: isPending ? 0.5 : 1 }}>
      <ResultList items={results} />
    </div>
  </>
);

프론트 심화

핵심 개념

댓글을 등록할 때 서버 저장이 끝날 때까지 화면이 멈춰 있는 대신, "성공할 거라고 낙관하고" 화면에 먼저 반영하는 패턴이 낙관적 업데이트입니다. 퍼블리싱으로 비유하면 진짜 데이터가 오기 전까지 임시 마크업을 오버레이로 얹어두는 것 — 데이터가 도착하면 임시 레이어는 자동으로 걷힙니다. React 19의 useOptimistic 훅은 이 임시 상태를 전용으로 관리하는데, 핵심은 일반 state와 달리 action(또는 transition)이 진행되는 동안에만 살아 있다가 끝나면 원본 데이터(props)로 자동 복귀한다는 점입니다. 지난주(07-15)에 본 Server Actions와 짝으로 쓰면 서버 저장 → revalidate → 진짜 데이터 교체까지 흐름이 자연스럽게 이어집니다. 

'use client';
import { useOptimistic } from 'react';
import { addComment } from './actions'; // Server Action

function Comments({ comments }: { comments: Comment[] }) {
  // [보여줄 목록, 임시 항목 추가 함수] = useOptimistic(원본, 병합 방법)
  const [optimisticComments, addOptimistic] = useOptimistic(
    comments,
    (current, newItem: Comment) => [...current, newItem]
  );

  async function handleSubmit(formData: FormData) {
    addOptimistic({ id: crypto.randomUUID(), text: String(formData.get('text')), pending: true });
    await addComment(formData); // 완료되면 revalidate → 진짜 데이터로 자동 교체
  }

  return (
    <form action={handleSubmit}>
      <ul>
        {optimisticComments.map(c => (
          <li key={c.id} style={{ opacity: c.pending ? 0.5 : 1 }}>{c.text}</li>
        ))}
      </ul>
      <input name="text" />
    </form>
  );
}

왜 알아야 하나

좋아요·댓글·장바구니처럼 "누르면 즉시 반응해야 하는" UI에서 체감 속도를 크게 올려주는 실무 필수 패턴입니다. 예전엔 useState 복제 + 실패 시 수동 롤백을 직접 짜야 했지만, useOptimistic은 실패하면 원본으로 자동 복귀하므로 롤백 코드가 사라집니다.

2026-07-16 (목) · 세션 vs JWT: 서버는 로그인한 나를 어떻게 기억할까

클라우드·백엔드 기초

핵심 개념

HTTP는 원래 무상태(stateless) — 요청 하나하나가 서로를 모르는 사이라, 매 요청마다 "나 아까 로그인한 그 사람이야"를 증명해야 합니다. 세션은 로그인 성공 시 서버가 명부(세션 저장소)에 기록하고 브라우저에는 번호표(세션 ID)만 쿠키로 주는 방식 — 클럽 보관소 번호표처럼 번호표 자체엔 정보가 없고 진실은 서버 명부에 있어요. JWT는 서버가 서명한 출입증을 통째로 주는 방식 — 이름·권한 같은 정보가 토큰 안에 들어 있고, 서버는 아무것도 저장하지 않은 채 서명만 검증합니다(위조방지 홀로그램이 찍힌 자유이용권). 트레이드오프: 세션은 서버가 즉시 강제 로그아웃시킬 수 있지만 저장소가 필요하고, JWT는 저장소 없이 검증돼 서버 확장에 유리하지만 한번 발급하면 만료 전까지 서버가 강제로 끊기 어렵습니다. 

// JWT = header.payload.signature 세 덩어리 (Base64 인코딩 — 암호화 아님!)
const token = jwt.sign({ userId: 42, role: 'user' }, SECRET, { expiresIn: '1h' });

// 검증: "이 서명이 우리 SECRET으로 만든 게 맞나?"를 다시 계산해서 비교
const payload = jwt.verify(token, SECRET); // 위조·만료면 throw

// ⚠️ payload는 누구나 디코딩해 읽을 수 있다.
// 서명은 "위조 방지"지 "암호화"가 아님 → 민감정보 넣지 말 것

어제(07-15) Server Actions에서 "자동 생성된 공개 엔드포인트라 함수 안에서 인증을 직접 해야 한다"고 했는데, 그 인증이 바로 이 이야기입니다. Auth.js(NextAuth) 같은 라이브러리도 내부적으로 세션/JWT 전략 중 하나를 고르게 되어 있어서, 이 차이를 알아야 설정과 디버깅이 가능해요.

// app/posts/actions.ts
'use server'; // 이 파일의 함수들은 서버에서만 실행

export async function createPost(formData: FormData) {
  const title = formData.get('title') as string;
  if (!title?.trim()) return { error: '제목을 입력하세요' };
  await db.post.create({ data: { title } }); // 서버니까 DB 직접 접근 OK
  revalidatePath('/posts'); // 목록 캐시 갱신
}

// app/posts/new/page.tsx — 서버 컴포넌트

      <button type="submit">등록</button>
    </form>
  );
}

2026-07-13 (월) · Suspense와 스트리밍 SSR: 느린 부분만 나중에 채워 넣기

프론트 심화

핵심 개념

지난 시간(07-03)에 서버 컴포넌트가 서버에서 HTML을 구워 내려보낸다고 했는데, 문제는 페이지 안에 느린 데이터 하나만 있어도 전체 HTML 완성이 그만큼 늦어진다는 거예요. Suspense는 "이 부분은 아직 준비 안 됐으면 임시 UI(fallback)를 먼저 보여줘"라고 선을 긋는 경계(boundary)입니다. 퍼블리싱으로 치면, 시안 하나가 늦는다고 페이지 전체 오픈을 미루는 게 아니라 — 레이아웃과 완성된 영역은 먼저 내보내고, 늦는 영역만 스켈레톤을 끼워뒀다가 도착하면 교체하는 방식이에요. 서버는 준비된 HTML부터 조각(chunk) 단위로 흘려보내고(스트리밍), 느린 컴포넌트가 완성되면 그 조각을 뒤이어 보내 브라우저가 fallback 자리를 갈아끼웁니다. Next.js App Router의 loading.tsx는 이걸 라우트(페이지) 단위로 자동 적용해 주는 관례 파일이에요. 

// app/dashboard/page.tsx — 서버 컴포넌트
import { Suspense } from 'react';

export default function Dashboard() {
  return (
    <>
      <Header />  {/* 빠름 → 즉시 스트리밍 */}
      <Suspense fallback={<CartSkeleton />}>
        <SlowCart />  {/* 느린 API → 준비되면 교체 */}
      </Suspense>
    </>
  );
}

async function SlowCart() {
  const cart = await fetchCart(); // 3초 걸려도 페이지 전체를 막지 않음
  return <CartView items={cart.items} />;
}

app/dashboard/loading.tsx 파일을 만들면 page 전체가 자동으로 <Suspense fallback={<Loading />}>에 감싸진 것과 같은 효과입니다. 경계를 어디에 두느냐가 설계 포인트 — 느린 컴포넌트만 콕 집어 감싸면 나머지는 즉시 보입니다.

왜 알아야 하나

"API 하나가 느려서 페이지 전체가 하얗게 멈춰 있는" 상황을 경계 하나로 해결할 수 있어요. 그리고 fallback으로 넣을 스켈레톤 UI 설계는 마크업 감각이 그대로 강점이 되는 영역입니다 — 실제 콘텐츠와 높이·구조가 같아야 교체 시 화면이 덜컹(CLS)하지 않거든요.

그동안 useState·useEffect·useRef·useReducer를 하나씩 봤는데, 오늘은 그걸 조합해서 내 함수로 뽑는 이야기입니다. 퍼블리싱에서 반복되는 마크업을 include/partial로 빼서 여러 페이지가 재사용했듯, 여러 컴포넌트에서 반복되는 상태 + 이펙트 로직을 use로 시작하는 함수 하나로 묶은 게 커스텀 훅이에요. 커스텀 훅이 공유하는 건 로직이지 상태값이 아닙니다 — 두 컴포넌트가 같은 훅을 호출해도 state는 각자 독립이에요(06-18 Context가 "값"을 공유한 것과 정반대 포인트). 규칙 하나: 이름이 반드시 use로 시작해야 React가 훅으로 인식하고 훅 규칙(조건문·반복문 안에서 호출 금지 등)을 검사해 줍니다. 

function useDebounce(value, delay = 300) {
  const [debounced, setDebounced] = useState(value);
  useEffect(() => {
    const id = setTimeout(() => setDebounced(value), delay);
    return () => clearTimeout(id); // 새 입력이 오면 이전 예약 취소
  }, [value, delay]);
  return debounced;
}

// 사용: 반복 로직이 컴포넌트에서 사라짐
function Search() {
  const [q, setQ] = useState('');
  const debouncedQ = useDebounce(q, 300);
  useEffect(() => { /* debouncedQ 로만 API 호출 */ }, [debouncedQ]);
  return <input value={q} onChange={(e) => setQ(e.target.value)} />;
}

2026-07-01 (수) · ref를 컴포넌트로 넘기기: forwardRef와 React 19의 "ref as prop"

프론트 심화

핵심 개념

06-22에서 ref를 <input ref={...}>처럼 DOM에 직접 붙였죠. 그런데 내가 만든 컴포넌트 <MyInput ref={...} />에 똑같이 넘기면 안 먹어요. ref는 key처럼 React가 가로채는 예약된 이름이라, 일반 prop과 달리 자식 함수 컴포넌트로 자동 전달되지 않기 때문입니다. 퍼블리싱에 비유하면, 내가 만든 래퍼 태그로 <input>을 감싸버려서 바깥에서 준 참조가 안쪽 실제 입력칸까지 닿지 못하는 상황이에요. 전통적 해법은 forwardRef로 컴포넌트를 감싸 두 번째 인자로 받은 ref를 내부 DOM에 연결하는 것. 그리고 React 19부터는 ref가 그냥 일반 prop처럼 함수 인자 (props.ref)로 들어와서 forwardRef 없이도 됩니다. 부모에게 DOM 전체 대신 focus() 같은 특정 동작만 노출하고 싶으면 useImperativeHandle을 씁니다. 

// 전통(React 18): forwardRef로 ref를 받아 내부 input에 연결
const MyInput = forwardRef(function MyInput({ label }, ref) {
  return <label>{label}<input ref={ref} /></label>;
});

// React 19: ref가 그냥 prop — forwardRef 불필요
function MyInput({ label, ref }) {
  return <label>{label}<input ref={ref} /></label>;
}

// 부모: 자식 내부 input에 포커스
const ref = useRef(null);
<MyInput label="이름" ref={ref} />;
// ref.current.focus();

// 일부 기능만 노출하고 싶으면
useImperativeHandle(ref, () => ({ focus: () => inputRef.current.focus() }));

왜 알아야 하나

ShadCN 커스텀 Input이나 react-hook-form의 register(ref 기반)를 내가 만든 컴포넌트에 연결할 때 바로 이 개념이 필요해서, "왜 내 컴포넌트엔 ref가 안 먹지?"를 즉시 풀 수 있습니다.

ⓐ ref는 비동기라 다음 렌더에 들어온다   ⓑ ref는 key처럼 React 예약어라 일반 prop으로 자동 전달되지 않는다   ⓒ 함수 컴포넌트는 DOM이 없다   ⓓ ref는 문자열로만 넘길 수 있다

2) (문제점 찾기) 아래 코드(React 18)에서 버튼을 눌러도 콘솔에 경고가 뜨고 ref.current가 null입니다. 왜이고, 어떻게 고칠까요?

정답·해설 보기

1) 정답 ⓑ — ref(와 key)는 React가 특별 취급하는 예약된 이름이라 props 객체에 담겨 자식 함수 컴포넌트로 넘어가지 않습니다. 그래서 React 18에서는 forwardRef로 감싸야 두 번째 인자로 ref를 받을 수 있어요. (ⓐ·ⓒ·ⓓ는 사실이 아님 — 함수 컴포넌트도 내부에 DOM을 가질 수 있고, ref는 객체로 넘깁니다.)

2) MyInput이 ref를 받지도, 내부 <input>에 연결하지도 않아서 ref.current가 계속 null이고, React 18은 "Function components cannot be given refs" 경고를 냅니다. 고치려면 forwardRef로 감싸 ref를 내부 input에 넘기면 됩니다: const MyInput = forwardRef(({ label }, ref) => <input ref={ref} placeholder={label} />). React 19라면 ref를 일반 prop으로 받아 (function MyInput({ label, ref }) { ... }) 그대로 연결하면 됩니다.

2026-06-30 (화) · HTTP 캐싱: Cache-Control vs ETag

클라우드·백엔드 기초

핵심 개념

퍼블리싱 때 CSS·이미지가 안 바뀌어서 "강력 새로고침(Ctrl+Shift+R)"을 눌러본 적 있죠? 그게 바로 HTTP 캐싱입니다. 브라우저는 한 번 받은 응답을 재사용해 네트워크를 아끼는데, 방식이 두 축이에요. ① 강한 캐시(Cache-Control: max-age=…) — 정한 시간 동안 서버에 아예 안 물어보고 캐시본을 씁니다. ② 조건부 요청(ETag/Last-Modified) — 만료 뒤 "이거 바뀌었어?"만 물어보고, 안 바뀌었으면 본문 없는 304 Not Modified로 데이터를 아낍니다. 비유하면 강한 캐시는 "한 달 유효" 도장이 찍힌 전단지, 조건부 요청은 도장 만료 후 "새 버전 나왔나요?"만 전화로 확인하는 것. 그래서 실무에선 정적 자산은 파일명 해시 + immutable로 영구 캐시하고, HTML·API는 no-cache로 매번 검증합니다. 

# 정적 자산(빌드 해시 파일): 1년 캐시 + 불변
Cache-Control: public, max-age=31536000, immutable

# HTML·데이터: 저장하되 매번 재검증
Cache-Control: no-cache
ETag: "a1b2c3"

# 재요청 시 브라우저가 자동으로 덧붙임
If-None-Match: "a1b2c3"
# 안 바뀌었으면 → HTTP/1.1 304 Not Modified  (본문 없음, 빠름)

왜 알아야 하나

Next.js 빌드 산출물(/_next/static/…)이 파일명 해시로 immutable 캐싱되는 이유, 그리고 "배포했는데 왜 옛 화면이 보이지?" 류 이슈와 API 응답 캐싱 튜닝이 전부 이 헤더 이해에서 출발합니다.

더 보기: MDN: Cache-Control · web.dev: HTTP caching

오늘의 퀴즈

1) (객관식) Cache-Control: no-cache의 의미로 옳은 것은?
ⓐ 절대 캐시하지 않는다   ⓑ 캐시는 저장하되 쓰기 전 서버에 재검증한다   ⓒ 딱 1초만 캐시한다   ⓓ 브라우저 캐시만 끄고 CDN은 캐시한다

2) (실전) 파일 app.js를 Cache-Control: public, max-age=31536000로 1년 캐시했습니다. 배포로 내용이 바뀌었는데 사용자는 계속 옛 파일을 봅니다. 왜 그럴까요? 또 번들러(Webpack/Vite 등)가 쓰는 표준 해결책은 무엇일까요?

정답·해설 보기

1) 정답 ⓑ — no-cache는 "캐시를 저장하되, 사용 전 매번 서버에 재검증(조건부 요청)하라"는 뜻입니다. 아예 저장조차 안 하는 건 no-store예요. 이름 때문에 헷갈리지만 no-cache ≠ no-store.

2) max-age(1년) 동안 브라우저는 서버에 묻지 않고 캐시본을 그대로 쓰기 때문에 바뀐 파일을 못 봅니다. 표준 해결책은 파일명에 콘텐츠 해시를 넣는 것(app.4f3a9c.js) — 내용이 바뀌면 파일명(URL)이 달라져 캐시 미스가 나고 새 파일을 받습니다. 그래서 해시가 박힌 파일엔 immutable을 붙여 영구 캐시해도 안전하죠(Next.js·Vite가 자동으로 해주는 방식).

핵심 개념

지난주 useRef·useReducer·memo를 보며 "렌더"를 다뤘는데, 오늘은 그 렌더가 만든 함정 하나를 봅니다. React 함수 컴포넌트는 렌더될 때마다 함수 전체가 다시 실행되고, 그 순간의 state 값이 스냅샷처럼 함수 안에 박제됩니다. 그래서 useEffect나 setInterval에 넘긴 콜백이 특정 렌더의 state를 클로저로 붙잡으면, 이후 state가 바뀌어도 그 콜백은 옛 값만 봐요 — 이게 오래된 클로저(stale closure)입니다. 퍼블리싱에 비유하면, 콜백은 "촬영 당시 인화된 사진" 같아서 실제 인물(state)이 나이를 먹어도 사진 속 얼굴은 그대로예요. 해결은 셋 중 하나: ① 의존성 배열을 정확히 채워 콜백을 최신 렌더로 갱신, ② 함수형 업데이트(setCount(c => c + 1))로 "이전 값"을 React에게서 받기, ③ useRef에 최신 값을 담아 .current로 참조. 

function Timer() {
  const [count, setCount] = useState(0);
  useEffect(() => {
    const id = setInterval(() => {
      // ❌ 이 콜백은 첫 렌더의 count(=0)에 박제됨
      console.log(count);
    }, 1000);
    return () => clearInterval(id);
  }, []); // 빈 deps → 콜백이 갱신되지 않음
  return <button onClick={() => setCount(count + 1)}>{count}</button>;
}

// ✅ 함수형 업데이트면 항상 최신 값
setCount(c => c + 1);

왜 알아야 하나

타이머·이벤트 구독·디바운스·웹소켓 핸들러 같은 실무 useEffect에서 가장 흔하고 재현 어려운 버그가 바로 이것이라, "분명 state는 바뀌었는데 콜백 안에서는 옛날 값"일 때 원인을 바로 짚을 수 있습니다.

오늘의 퀴즈

1) (객관식) 다음 중 stale closure를 피하는 방법이 아닌 것은?
ⓐ setCount(c => c + 1)처럼 함수형 업데이트를 쓴다   ⓑ useEffect 의존성 배열에 콜백이 참조하는 state를 빠짐없이 넣는다   ⓒ 최신 값을 useRef의 .current에 넣고 콜백에서 ref.current를 읽는다   ⓓ 의존성 배열을 항상 빈 배열([])로 둬서 effect를 한 번만 만든다

2) (출력 예측 · 문제점 찾기) 아래 컴포넌트에서 마운트 후 버튼을 3번 누르면, 1초마다 콘솔에 무엇이 찍힐까요? 왜 그렇고, 어떻게 고칠까요? 

function Counter() {
  const [count, setCount] = useState(0);
  useEffect(() => {
    const id = setInterval(() => console.log(count), 1000);
    return () => clearInterval(id);
  }, []);
  return <button onClick={() => setCount(count + 1)}>{count}</button>;
}
정답·해설 보기

1) 정답 ⓓ — 의존성 배열을 빈 배열로 두면 effect 콜백이 첫 렌더의 state(스냅샷)에 영원히 묶여 오히려 stale closure의 직접 원인이 됩니다. ⓐ·ⓑ·ⓒ는 각각 최신 값을 "받는 / 갱신하는 / 참조하는" 올바른 회피법이에요.

2) 콘솔에는 1초마다 계속 0이 찍힙니다. 화면 숫자는 3으로 바뀌지만, setInterval 콜백은 빈 deps 때문에 첫 렌더에서 한 번 만들어져 그때의 count(=0)를 클로저로 붙잡고 있기 때문이에요(버튼 클릭은 새 렌더를 만들지만 인터벌은 재생성되지 않음). 고치려면 ① countRef.current = count로 ref에 최신 값을 동기화하고 콜백에서 countRef.current를 읽거나, ② 함수형 업데이트로 우회하거나, ③ 정말 매 변경마다 새로 찍어야 하면 deps에 [count]를 넣어 인터벌을 재설정합니다(이때는 cleanup의 clearInterval로 이전 타이머 정리가 필수).

2026-06-26 (금) · 제어 컴포넌트 vs 비제어 컴포넌트

프론트 심화

핵심 개념

퍼블리싱 때 <input>은 사용자가 타이핑하면 값이 그냥 DOM에 쌓였죠. 그게 바로 비제어(uncontrolled) 방식 — 값의 "진실"이 DOM에 있고, 필요할 때 ref로 꺼내봅니다. 반대로 제어(controlled)는 값의 진실을 React state가 쥐고, input은 그 state를 그대로 비추는 "거울"일 뿐입니다(value={state} + onChange로 갱신). 어제 리스트 input의 체크 상태가 한 칸씩 밀렸던 것도 결국 "입력값이 어디 사는가" 문제였는데, 제어/비제어는 그 질문의 정면입니다. 실무에선 react-hook-form·ShadCN Form이 기본은 비제어 (register, ref 기반)로 성능을 챙기고, 계산·동기화가 필요한 곳만 제어(Controller)로 씁니다. 

// 제어(controlled): 값의 단일 출처 = state
const [name, setName] = useState("");
<input value={name} onChange={(e) => setName(e.target.value)} />

// 비제어(uncontrolled): 값의 출처 = DOM, 제출 시 ref로 읽기
const ref = useRef(null);
<input ref={ref} defaultValue="" />
// onSubmit 시: ref.current.value

왜 알아야 하나

react-hook-form/ShadCN에서 register(비제어)와 Controller(제어)를 골라 쓰는 기준이 바로 이 개념이라, "왜 value가 안 먹지 / 왜 리렌더가 이렇게 잦지"를 디버깅할 때 바로 길이 보입니다.

더 보기: React: <input> (제어/비제어) · react-hook-form: Controller

오늘의 퀴즈

1) (객관식) 다음 중 제어 컴포넌트의 특징은?
ⓐ value 없이 defaultValue만 준다   ⓑ 값을 ref.current.value로 읽는다   ⓒ value={state} + onChange로 state가 값의 단일 출처다   ⓓ onChange 없이 value만 고정으로 준다

2) (문제점 찾기) 아래 코드에서 타이핑을 시작하면 콘솔 경고가 뜹니다: "A component is changing an uncontrolled input to be controlled." 왜 그렇고, 어떻게 고칠까요? 

const [v, setV] = useState();
<input value={v} onChange={(e) => setV(e.target.value)} />
정답·해설 보기

1) 정답 ⓒ — 제어 컴포넌트는 value={state}로 값의 단일 출처가 state이고 onChange로 그 state를 갱신합니다. ⓐ·ⓑ는 비제어(DOM이 값을 보관, ref로 읽음)의 특징이고, ⓓ처럼 value만 주고 onChange가 없으면 입력이 안 먹는 read-only가 되는 흔한 실수입니다.

2) 초기값을 안 줘서 useState()가 첫 렌더에 undefined를 반환합니다. 그래서 value={undefined}로 시작 → React는 이를 비제어로 보다가, 타이핑하면 value가 문자열로 바뀌어 제어로 전환되며 경고가 납니다. 해결: 초기값을 빈 문자열로 주면 (useState("")) 처음부터 끝까지 제어 컴포넌트로 일관됩니다.

2026-06-25 (목) · key & 재조정(reconciliation)

프론트 심화

핵심 개념

어제 React.memo로 "언제 다시 안 그릴지"를 봤다면, 오늘은 한 단계 더 들어가 React가 무엇을 바꿀지 정하는 과정, 재조정(reconciliation)입니다. React는 이전 가상 DOM 트리와 새 트리를 비교해 달라진 부분만 실제 DOM에 반영하는데, 리스트(.map())에서는 "이전 3번째 항목과 새 3번째 항목이 같은 것이냐"를 판단할 기준이 필요해요. 그 기준이 key입니다. 퍼블리싱에 비유하면, 목록을 다시 정렬할 때 각 <li>에 고유 번호표를 붙여두면 "이건 그대로, 이건 자리만 이동"이라고 콕 집어 알 수 있지만, 번호표 없이 "위에서 몇 번째"로만 세면 중간에 하나 끼어드는 순간 전부 밀려서 엉뚱한 칸을 고치게 됩니다. 그래서 key는 목록 안에서 안정적이고 고유한 값(주로 데이터의 id)이어야 하고, 배열 index는 순서가 바뀌거나 항목이 추가·삭제되면 같은 항목을 다른 key로 보게 만들어 입력값·포커스가 엉키는 버그를 냅니다. 

// ❌ index를 key로 — 항목 추가/삭제·정렬 시 상태가 엉킴
{items.map((item, i) => (
  <Row key={i} item={item} />
))}

// ✅ 데이터 고유 id를 key로
{items.map((item) => (
  <Row key={item.id} item={item} />
))}

• key는 형제 사이에서만 고유하면 됩니다(전역 유일일 필요 X). • key는 props가 아니에요 — 자식에서 props.key로 못 읽습니다. 필요하면 따로 id prop으로 넘기세요. • 정렬·필터·추가·삭제가 전혀 없는 완전 고정 목록이면 index도 사고는 안 나지만, 습관적으로 id를 쓰는 게 안전합니다.

왜 알아야 하나

입력창이 든 리스트(체크박스 목록, react-hook-form의 useFieldArray, ShadCN 테이블 행)에서 index를 key로 쓰면 "행을 지웠는데 옆 행의 입력값이 따라 지워지는" 류의 재현 어려운 버그가 납니다. key를 id로 잡는 습관만으로 이 버그군 전체를 예방할 수 있어요.

오늘의 퀴즈

1) (객관식) 리스트의 key로 가장 적절한 값은?
ⓐ 배열의 index (0, 1, 2…)   ⓑ 매 렌더마다 새로 만든 Math.random()   ⓒ 데이터의 고유 id (예: item.id)   ⓓ 항목의 표시 텍스트(중복될 수 있음)

2) (문제점 찾기) 아래 리스트에서 맨 앞 항목을 삭제하면, 남은 행들의 체크 상태가 한 칸씩 밀려 엉뚱한 행이 체크된 것처럼 보입니다. 왜이고, 어떻게 고칠까요? 

{todos.map((todo, i) => (
  <li key={i}>
    <input type="checkbox" /> {todo.text}
  </li>
))}
정답·해설 보기

1) 정답 ⓒ (데이터의 고유 id) — key는 목록 안에서 안정적이고 고유해야 합니다. index(ⓐ)는 순서·개수가 바뀌면 같은 항목이 다른 key가 되고, Math.random()(ⓑ)은 매 렌더마다 key가 바뀌어 React가 전부 새 항목으로 보고 통째로 다시 만듭니다(상태·포커스 소실). 텍스트(ⓓ)는 중복·변경 가능성이 있어 부적합합니다. 그래서 변하지 않는 데이터의 id가 정답이에요.

2) 체크 상태는 <input> DOM 노드에 묶여 있는데, key가 index라 맨 앞을 지우면 나머지 항목의 key가 한 칸씩 당겨집니다(이전 key=1이던 항목이 이제 key=0). React는 "key 0 자리는 그대로네"라고 보고 이전 노드(와 그 체크 상태)를 새 todo에 재사용하기 때문에 체크가 한 칸 밀린 것처럼 보입니다. 해결: key={todo.id}처럼 항목 고유 id를 key로 주면, 항목이 이동·삭제돼도 React가 같은 항목을 추적해 체크 상태가 올바른 행을 따라갑니다.
