1. 학습 목표 (심화)

기초편이 "동작하는 화면 만들기"였다면, 심화편은 왜 빠르고/느린지, 왜 다시 그려지는지, 대규모에서 어떻게 무너지지 않는지를 다룹니다.

렌더링 내부성능동시성타입 안정성아키텍처

최종적으로 할 수 있어야 하는 말

"이 리스트는 항목이 많아 가상화하고, 무거운 계산은 메모이즈한다. 이 입력은 급하지 않으니 transition으로 낮은 우선순위로 처리하고, 라우트 단위로 코드 스플리팅한다. 디자인 토큰으로 스타일을 일관되게 묶고, 컴포넌트는 role 기준으로 테스트한다."

2. 렌더링 성능 & Core Web Vitals

Reflow vs Repaint vs Composite

변경 발생 단계 비용
width, top, font-size 등 기하 Reflow → Repaint → Composite 가장 무거움
color, background 등 Repaint → Composite 중간
transform, opacity Composite만 가장 가벼움 (GPU)

Layout Thrashing

스타일을 바꾼 직후 레이아웃 값을 읽으면(offsetHeight 등) 브라우저가 강제로 즉시 레이아웃을 계산합니다. 읽기/쓰기를 번갈아 하면 이게 반복돼 급격히 느려집니다.

// 나쁨: 읽기-쓰기가 섞여 매번 강제 reflow
items.forEach((el) => { el.style.height = el.offsetHeight + 10 + "px"; });

// 좋음: 읽기 모아서 → 쓰기 모아서
const hs = items.map((el) => el.offsetHeight);
items.forEach((el, i) => { el.style.height = hs[i] + 10 + "px"; });

Core Web Vitals

구글이 정의한 실사용 성능 지표입니다.

지표 의미 좋음 기준
LCP 가장 큰 콘텐츠가 보이기까지 (로딩) 2.5초 이하
CLS 레이아웃이 갑자기 밀리는 정도 (안정성) 0.1 이하
INP 상호작용에 대한 응답 속도 (반응성, FID 대체) 200ms 이하
프론트에서의 실천

이미지·광고 영역에 크기를 미리 지정하면 CLS가 줄고, 무거운 JS를 쪼개면 INP가 좋아집니다. LCP는 보통 핵심 이미지·폰트 로딩을 앞당겨 개선합니다.

3. React 렌더링 내부: 재조정 & Fiber

재조정(Reconciliation)

state가 바뀌면 React는 새 가상 트리를 만들고, 이전 트리와 비교해 달라진 부분만 실제 DOM에 반영합니다. 이때 key로 어떤 항목이 같은지 식별합니다. key가 인덱스면 순서가 바뀔 때 엉뚱한 항목이 재사용됩니다.

Fiber 아키텍처

React 16부터의 렌더링 엔진입니다. 렌더링을 작은 작업 단위로 쪼개 중단·재개·우선순위 조정이 가능합니다. 덕분에 긴 렌더링이 사용자 입력을 막지 않습니다.

단계 설명
Render 단계 가상 트리 계산·비교. 중단·폐기 가능 (화면에 아직 반영 안 함)
Commit 단계 계산 결과를 실제 DOM에 한 번에 반영. 중단 불가
왜 알아야 하나

Render 단계는 여러 번 실행되거나 버려질 수 있어서, 그 안에 부수효과(API 호출 등)를 넣으면 안 됩니다. 부수효과는 useEffect(커밋 이후)에 둬야 하는 이유가 여기 있습니다.

4. React 최적화: memo · 가상화

메모이제이션 3종

도구 역할
React.memo props가 같으면 컴포넌트 리렌더 생략
useMemo 무거운 계산 결과를 캐시
useCallback 함수의 참조를 유지 (자식 memo와 짝)
남용 주의

메모이제이션도 비교 비용이 듭니다. 측정 없이 모든 곳에 붙이면 오히려 느리고 코드만 복잡해집니다. "느린 게 확인된 곳"에만 쓰세요. 참고로 React 19의 컴파일러는 이런 메모이제이션을 상당 부분 자동화하는 방향입니다.

리스트 가상화

수천 개 항목을 전부 DOM에 그리면 느립니다. 화면에 보이는 부분만 그리고 스크롤에 따라 교체하는 것이 가상화입니다(react-window, TanStack Virtual 등).

전체 10,000개 → 보이는 ~20개만 실제 DOM 스크롤 시 위/아래 항목을 재활용해 교체

5. Concurrent & Suspense

React 18+의 동시성 기능은 "급한 업데이트"와 "안 급한 업데이트"를 구분해 반응성을 지킵니다.

useTransition / useDeferredValue

const [isPending, startTransition] = useTransition();

function onChange(e) {
  setQuery(e.target.value);            // 급함: 입력은 즉시 반영
  startTransition(() => {
    setResults(search(e.target.value)); // 안 급함: 결과는 낮은 우선순위
  });
}

입력은 끊김 없이 반영되고, 무거운 결과 렌더링은 뒤로 미뤄 화면이 버벅이지 않습니다.

Suspense

데이터·코드가 준비될 때까지 fallback(스켈레톤 등)을 보여주는 선언적 로딩 처리입니다.

<Suspense fallback={<Skeleton />}>
  <UserProfile id={id} />
</Suspense>
SSR과의 연결

스트리밍 SSR에서는 Suspense 경계 단위로 준비된 부분부터 HTML을 흘려보냅니다. 느린 위젯 하나가 전체 페이지를 막지 않게 됩니다.

6. 상태 관리 심화

Context의 함정

Context 값이 바뀌면 그 값을 구독하는 모든 컴포넌트가 리렌더됩니다. 자주 바뀌는 값을 큰 Context에 담으면 광범위한 리렌더가 일어납니다.

  • 변경 빈도가 다른 값은 Context를 분리
  • 외부 스토어(Zustand 등)는 필요한 조각만 구독해 리렌더를 줄임
  • 외부 스토어를 React와 안전하게 연결할 땐 useSyncExternalStore

상태를 어디에 둘 것인가

질문 결론
서버에서 온 데이터인가? React Query (서버 상태)
여러 화면이 공유하는가? 전역 스토어 or Context
한 컴포넌트만 쓰는가? 로컬 useState — 가능한 가장 가까운 곳에
핵심 원칙

"상태를 필요한 곳 가장 가까이 둔다(colocation)." 무턱대고 전역으로 올리면 결합도가 높아지고 리렌더가 늘어납니다.

7. 로딩 최적화: 코드 스플리팅

모든 코드를 한 번에 내려받으면 초기 로딩이 느립니다. 필요한 시점에 나눠 받습니다.

import { lazy, Suspense } from "react";
const Settings = lazy(() => import("./Settings"));

<Suspense fallback={<Spinner />}>
  <Settings />   {/* 이 화면에 들어갈 때 비로소 다운로드 */}
</Suspense>
  • 라우트 단위 분할: 페이지별로 나누는 게 가장 효과적
  • 프리페치: 곧 쓸 청크를 미리 받아 체감 지연 제거
  • 이미지: 적절한 포맷(WebP/AVIF)·사이즈·lazy 로딩
  • 폰트: font-display: swap으로 텍스트 즉시 표시

8. 번들링 심화: Tree Shaking

Tree shaking은 실제로 쓰지 않는 코드를 번들에서 제거하는 것입니다. ESM의 정적 import 구조 덕에 가능합니다.

// 전체를 가져오면 안 쓰는 것도 포함될 수 있음
import _ from "lodash";
// 필요한 것만 → tree shaking에 유리
import debounce from "lodash/debounce";
개념 설명
ESM vs CommonJS ESM은 정적 분석이 가능해 tree shaking에 유리. CJS(require)는 어려움
sideEffects package.json의 이 필드로 "제거해도 안전한 모듈"을 표시
청크 전략 공통 라이브러리를 별도 청크로 빼 캐시 적중률을 높임

Vite·webpack·Turbopack 같은 번들러가 이 과정을 수행합니다. 번들 분석 도구로 무엇이 무거운지 확인하는 습관이 중요합니다.

9. TypeScript

타입은 런타임 전에 실수를 잡고, 자동완성과 리팩터링 안정성을 줍니다.

자주 쓰는 유틸리티 타입

타입 의미
Partial<T> 모든 속성을 선택적으로
Pick<T, K> / Omit<T, K> 일부 속성만 고르기 / 빼기
Record<K, V> 키-값 형태의 객체 타입

컴포넌트와 API 타이핑

type ButtonProps = {
  variant: "primary" | "ghost";   // 좁은 유니온으로 오용 방지
  onClick: () => void;
  children: React.ReactNode;
};

function Button({ variant, onClick, children }: ButtonProps) { /* ... */ }

// API 응답도 타입으로 고정
type User = { id: number; name: string };
const res = await api.get<User[]>("/users");
좁히기(narrowing)

판별 가능한 유니온(discriminated union)으로 상태를 모델링하면, 로딩/성공/에러를 타입 수준에서 안전하게 분기할 수 있습니다. 예: { status: "success"; data } | { status: "error"; error }

10. 접근성 심화: WCAG · 포커스

기초편의 시맨틱·alt·label 위에, 동적 UI에서 자주 놓치는 부분입니다.

키보드 & 포커스 관리

  • 모달이 열리면 포커스를 모달 안으로 이동하고, 안에 가둔다(focus trap)
  • 모달이 닫히면 열기 전 요소로 포커스를 되돌린다
  • Tab 순서가 시각적 순서와 일치해야 한다
  • 커스텀 위젯엔 적절한 role과 키보드 동작을 직접 구현

동적 변화 알림 (Live Region)

<div aria-live="polite">{message}</div>
<!-- 내용이 바뀌면 스크린리더가 읽어줌 (polite: 끼어들지 않게) -->

WCAG 기준

실무 목표는 보통 WCAG 2.1 AA입니다. 대표적으로 본문 텍스트 대비 4.5:1 이상, 모든 기능의 키보드 사용 가능, 콘텐츠가 색에만 의존하지 않기 등이 있습니다.

강점 살리기

접근성은 마크업·표준에 능한 사람일수록 잘하는 영역입니다. 컴포넌트를 만들 때 접근성을 기본값으로 넣어두면, 팀 전체의 품질 기준이 올라갑니다.

11. CSS 아키텍처 & 디자인 시스템

규모가 커지면 "동작하는 CSS"보다 "충돌·중복 없이 확장되는 CSS"가 중요해집니다.

스타일링 전략 비교

방식 특징
CSS Modules 클래스명을 지역 스코프로 격리. 충돌 없음
CSS-in-JS JS로 스타일 작성. 동적 스타일에 강함(런타임 비용 고려)
유틸리티 (Tailwind) 작은 클래스 조합. 빠른 작업·일관성, 마크업이 길어짐

디자인 토큰

색·간격·타이포를 변수로 정의해 한 곳에서 관리합니다. 디자인 시스템의 기반입니다.

:root {
  --color-primary: #2563eb;
  --space-2: 8px;
  --radius-md: 12px;
}
.button { background: var(--color-primary); padding: var(--space-2); }

모던 CSS 무기

  • @layer: 캐스케이드 레이어로 우선순위를 명시적으로 관리(!important 의존 감소)
  • 컨테이너 쿼리: 뷰포트가 아닌 부모 크기에 반응 → 진짜 재사용 가능한 컴포넌트
  • :has(): 부모를 자식 조건으로 선택하는 관계형 선택자
디자인 시스템 관점

토큰 → 프리미티브 컴포넌트 → 합성 컴포넌트로 쌓아 올리면, 디자인과 코드가 같은 언어를 쓰게 됩니다. 이것이 디자인 엔지니어링의 핵심 골격입니다.

12. 테스트

테스트는 "리팩터링해도 안 깨진다"는 안전망입니다. 종류별로 목적이 다릅니다.

종류 대상 도구
단위 함수·훅 하나 Vitest, Jest
통합 컴포넌트 + 상호작용 Testing Library
E2E 실제 브라우저 사용자 흐름 Playwright, Cypress 
// Testing Library: 구현이 아니라 "사용자가 보는 것"을 테스트
const btn = screen.getByRole("button", { name: "저장" });
await user.click(btn);
expect(screen.getByText("저장됨")).toBeInTheDocument();
철학과 네트워크 모킹

클래스명·내부 state가 아니라 role·텍스트로 찾으면, 접근성도 챙기고 리팩터링에도 강한 테스트가 됩니다. API는 MSW로 네트워크 레벨에서 모킹하면 실제와 가깝게 검증할 수 있습니다.

13. 심화 체크리스트

  • □ reflow/repaint/composite를 유발하는 속성을 구분한다.
  • □ layout thrashing을 알고 읽기/쓰기를 분리한다.
  • □ LCP·CLS·INP의 의미와 개선 방향을 안다.
  • □ 재조정과 key의 역할을 설명할 수 있다.
  • □ Fiber의 render/commit 단계 분리를 안다.
  • □ memo/useMemo/useCallback을 측정 기반으로 쓴다.
  • □ 긴 리스트를 가상화로 처리할 수 있다.
  • □ useTransition으로 우선순위를 나눌 수 있다.
  • □ Suspense로 로딩을 선언적으로 처리한다.
  • □ Context 리렌더 함정과 외부 스토어를 안다.
  • □ 상태를 필요한 곳 가까이 두는 원칙을 안다.
  • □ 라우트 단위 코드 스플리팅을 적용한다.
  • □ tree shaking과 ESM의 관계를 안다.
  • □ 유틸리티 타입과 컴포넌트 타이핑을 한다.
  • □ 판별 유니온으로 상태를 안전하게 모델링한다.
  • □ 모달 포커스 관리와 live region을 구현한다.
  • □ WCAG 2.1 AA 핵심 기준을 안다.
  • □ 스타일링 전략과 디자인 토큰을 설명할 수 있다.
  • □ @layer·컨테이너 쿼리·:has()를 활용한다.
  • □ 단위/통합/E2E의 목적을 구분하고 role 기준으로 테스트한다.
