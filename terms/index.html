API Gateway

Stale-While-Revalidate 캐시 전략

React Query 심화
캐시된 데이터를 즉시 보여주고, 뒤에서 조용히 최신 데이터를 가져와서 교체하는 패턴. 로딩 스피너 없이 즉각 반응.
TanStack Query에서
staleTime: 이 시간 동안 캐시를 fresh로 간주 (재검증 안 함) / gcTime: 이 시간 후 캐시 제거

React Query 심화 캐시 생명주기

Optimistic UpdateStale-While-Revalidate

캐시 상태

  • fresh: staleTime 내 → 재검증 안 함
  • stale: 만료됨 → 백그라운드 재검증
  • inactive: 언마운트됨 → gcTime 카운트
  • deleted: gcTime 후 캐시 제거

주요 함수

  • invalidateQueries: stale로 표시 → 다음 사용 시 재검증
  • refetchQueries: 즉시 재요청
  • setQueryData: 캐시 직접 수정 (Optimistic에 사용)
  • prefetchQuery: 미리 가져오기

Hydration / Dehydration

RSC vs RCCStreaming·SuspenseCritical Rendering Path
SSR에서 서버가 만든 HTML에 React가 이벤트 핸들러를 붙이는 과정이 Hydration. "use client" 경계가 바로 이 구분선.

Dehydration (건조)

  • React 상태를 JSON으로 직렬화
  • HTML에 담아서 전송
  • 서버에서 일어남

Hydration (수화)

  • JSON을 브라우저에서 React 상태로 복원
  • 이벤트 핸들러 부착
  • 이 시점 전까지 클릭해도 반응 없음

Edge Runtime vs Node.js Runtime

Edge Runtime

  • CDN 가까이 실행 → 초고속
  • Node.js API 사용 불가
  • 미들웨어 기본값
  • 인증 체크, 리다이렉트에 적합

Node.js Runtime

  • 원격 서버 실행
  • 모든 Node.js API 가능
  • DB 직접 쿼리 (Prisma 등)
  • 파일 시스템 접근 가능
흔한 실수
미들웨어에서 Prisma 쓰다 에러 → Edge에서 Node.js API 호출한 것

RSC vs RCC Server Component vs Client Component

HydrationFiber 아키텍처

RSC (Server Component)

  • 기본값 (선언 없어도 RSC)
  • DB, 파일 시스템 직접 접근
  • useState, useEffect 사용 불가
  • 번들 사이즈에 포함 안 됨 → 성능 유리

RCC (Client Component)

  • "use client" 선언 필요
  • useState, useEffect 사용 가능
  • 이벤트 핸들러 사용 가능
  • Hydration 대상 → JS 번들에 포함
판단 기준
상호작용(클릭, 입력, 상태)이 필요하면 RCC. 데이터 fetching·서버 전용 로직은 RSC. 가능하면 RSC 우선 → 번들 사이즈 감소.

Streaming + Suspense 점진적 렌더링

RSCHydration
전체 페이지가 준비될 때까지 기다리지 않고 준비된 부분부터 즉시 전송. Suspense로 감싼 컴포넌트는 데이터 준비될 때 채워짐.
Next.js 사용법
<Suspense fallback={<Skeleton />}> <SlowDataComponent /> // 2초 걸리는 API </Suspense> // 나머지 페이지는 즉시 표시, SlowDataComponent만 나중에 채워짐

CORS 교차 출처 리소스 공유

Token 저장 전략CSRF·SameSite
브라우저가 다른 출처(Origin)의 API 요청을 기본으로 차단하는 보안 정책. 서버끼리 통신에는 없음.
해결: 백엔드가 Access-Control-Allow-Origin 헤더 추가.

Token 저장 전략 Cookie vs LocalStorage

OAuth·OIDCCSRF·SameSite

LocalStorage ⚠

  • JS로 자유롭게 읽기 가능
  • XSS 공격 시 토큰 탈취 가능
  • 악성 스크립트가 getItem으로 훔쳐감

HttpOnly Cookie ✓

  • JS에서 접근 불가
  • 서버만 읽을 수 있음
  • XSS로 훔칠 수 없음
  • CSRF 주의 → SameSite로 완화

OAuth 2.0 / OIDC 인증·인가 프로토콜

Token 저장 전략

OAuth 2.0

  • 권한 위임(Authorization) 프로토콜
  • "이 앱이 내 데이터에 접근해도 돼"

OIDC

  • OAuth 위에 인증(Authentication) 레이어
  • "이 사람이 누구인지" 신원 확인
Authorization Code Flow
① 브라우저 → IdP: 로그인 요청
② IdP → 브라우저: Authorization Code 발급
③ 브라우저 → 백엔드: Code 전달
④ 백엔드 → IdP: Code → Access Token 교환
⑤ 백엔드 → 브라우저: 세션 쿠키 발급
SaaSOps와 연결
SaaSOps가 IdP 역할 → PBU 전체 SSO를 SaaSOps IdP가 공급. 템플릿 C-3에 쓴 근거.

CSRF + SameSite 쿠키 보안

CSRF — 로그인된 사용자 모르게 악성 사이트에서 요청을 보내는 공격. 브라우저가 쿠키를 자동으로 보내는 것을 악용.

Strict

  • 다른 사이트 요청엔 쿠키 절대 안 보냄
  • 가장 안전, UX 불편

Lax (기본값)

  • 링크 클릭 등 GET만 허용
  • POST 차단, 일반적으로 권장

None

  • 모든 요청에 쿠키 포함
  • CSRF 취약, Secure 필수

Core Web Vitals LCP · INP · CLS

Datadog RUMLighthouse CI

LCP

  • 가장 큰 콘텐츠가 그려지는 시간

Code Splitting + Lazy Loading 번들 분할

Tree Shaking
초기 로딩에 필요한 코드만 먼저 다운로드하고, 나머지는 필요할 때 동적으로 가져오는 패턴.
React에서 구현
const Dashboard = React.lazy(() => import('./Dashboard')) <Suspense fallback={<Spinner />}> <Dashboard /> // 대시보드 진입 시에만 다운로드 </Suspense>

Tree Shaking 사용하지 않는 코드 제거

Tree Shaking 안 되는 경우

  • import _ from 'lodash' (전체 import)
  • CommonJS 모듈 (require)
  • Side effect 있는 코드

Tree Shaking 잘 되는 경우

  • import { debounce } from 'lodash-es'
  • ESM 모듈 (import/export)
  • Named export 사용

Memoization useMemo · useCallback · React.memo

Reconciliation
useMemo — 계산 비용 클 때 useCallback — 자식에 함수 전달 시 남용 주의 — 먼저 측정하고 최적화

React.memo

  • 컴포넌트를 메모이제이션
  • props가 바뀌지 않으면 리렌더링 스킵
  • 무거운 리스트 아이템에 적합

useMemo

  • 계산된 값을 메모이제이션
  • 의존성 바뀔 때만 재계산
  • 대용량 데이터 필터링·정렬

useCallback

  • 함수를 메모이제이션
  • 자식에게 함수 prop 전달 시 유용
  • React.memo와 함께 사용
남용 주의
메모이제이션 자체도 비용. 실제 성능 병목이 있을 때만 적용. 먼저 측정하고, 그다음 최적화.

Reflow + Repaint 렌더링 성능

Critical Rendering PathCompositor Layer

Reflow (비쌈)

  • 요소의 위치·크기 재계산
  • width, height, margin, top 변경 시
  • DOM 추가·제거 시
  • 전체 렌더 트리 영향 → 느림

Repaint (상대적으로 쌈)

  • 레이아웃 변경 없이 시각적 속성만 변경
  • color, background, border-color 변경 시
  • Reflow는 항상 Repaint를 유발
최소화 방법
// ✗ 매번 Reflow el.style.width = '100px'; el.style.height = '200px' // ✓ 클래스로 한번에 el.classList.add('expanded') // ✓ transform은 Reflow 없이 GPU 처리 → CLS 영향 없음 el.style.transform = 'translateX(100px)'

렌더링 파이프라인 브라우저 내부 동작

Compositor LayerCritical Rendering Path메인 스레드 최적화

메인 스레드에서 일어나는 것

  • JavaScript 실행
  • Style 계산 (CSS 적용)
  • Layout (위치·크기)
  • Paint (픽셀 기록)

컴포지터 스레드에서 일어나는 것

  • 레이어 합성 (GPU)
  • transform, opacity 애니메이션
  • 스크롤 (메인 스레드 없이 가능)
  • 메인 스레드 블로킹 없이 60fps
실무 적용
애니메이션은 transform/opacity만 써야 컴포지터 스레드에서 처리됨. width/height 애니메이션은 매 프레임마다 Layout + Paint → 버벅임.

Compositor Layer 레이어 분리

렌더링 파이프라인Reflow·Repaint
브라우저가 특정 요소를 별도 레이어로 분리해서 GPU에서 독립적으로 합성하는 것. 메인 스레드 없이 애니메이션 가능.

레이어 생성 조건

  • transform: translateZ(0) (레이어 강제 생성)
  • will-change: transform
  • position: fixed
  • video, canvas 요소

주의사항

  • 레이어가 너무 많으면 메모리 낭비
  • 불필요한 will-change 남용 금지
  • Chrome DevTools Layers 패널로 확인

메인 스레드 최적화 Long Task · Web Worker · rIC

렌더링 파이프라인이벤트 루프Web Worker
JS는 싱글 스레드. 메인 스레드가 50ms 이상 블로킹되면 Long Task로 분류되고 INP가 악화됨.

Long Task란

  • 메인 스레드를 50ms 이상 점유하는 작업
  • 이 동안 클릭·키보드 입력 반응 없음
  • Chrome DevTools Performance 패널에서 확인
  • INP 악화의 주원인

해결 방법

  • setTimeout(fn, 0)으로 작업 분할
  • 무거운 연산은 Web Worker로 오프로드
  • requestIdleCallback으로 유휴 시간 활용
  • 가상화 (react-window)로 DOM 노드 최소화
requestIdleCallback — 유휴 시간에 실행
requestIdleCallback((deadline) => { while (deadline.timeRemaining() > 0 && tasks.length > 0) { doWork(tasks.pop()) // 브라우저가 바쁘면 알아서 멈춤 } })

V8 엔진 · JIT 컴파일 JS가 빠른 이유

가비지 컬렉션메모리 구조

JIT (Just-In-Time) 컴파일

  • 처음엔 인터프리터로 빠르게 시작
  • 자주 실행되는 코드(Hot Code) 감지
  • 감지된 코드를 머신 코드로 최적화
  • 타입이 일정하면 최적화 유지

Deoptimization (역최적화)

  • 타입이 바뀌면 최적화 코드 폐기
  • 다시 인터프리터로 돌아감
  • 예: 배열에 다른 타입 섞기
  • 타입 일관성이 성능에 직결
실무 적용
TypeScript로 타입을 일관되게 유지하면 V8이 최적화 코드를 안정적으로 유지. 배열에 타입을 섞거나 객체 shape을 동적으로 바꾸면 deopt 발생.

가비지 컬렉션 Mark & Sweep

메모리 구조V8 엔진
JS는 메모리를 자동 관리함. 참조되지 않는 객체를 탐지해서 메모리를 해제하는 과정이 GC(Garbage Collection).

Mark & Sweep 동작

  • Mark: root에서 시작해 도달 가능한 객체에 표시
  • Sweep: 표시 안 된 객체(참조 없음) 메모리 해제
  • V8은 Minor GC(Young Gen)와 Major GC(Old Gen) 분리
  • GC 실행 중 메인 스레드 멈춤 → 주의

메모리 누수 원인

  • 전역 변수에 객체 계속 추가
  • 이벤트 리스너 미제거
  • 클로저가 큰 객체 참조 유지
  • setInterval 미해제
메모리 누수 예시 vs 올바른 패턴
// ✗ 누수: 이벤트 리스너 미제거 useEffect(() => { window.addEventListener('resize', handler) }, []) // ✓ cleanup 함수로 제거 useEffect(() => { window.addEventListener('resize', handler) return () => window.removeEventListener('resize', handler) }, [])

메모리 구조 Stack vs Heap

가비지 컬렉션V8 엔진

Stack

  • 원시값 (number, boolean, string)
  • 함수 호출 정보 (실행 컨텍스트)
  • 크기 고정, 빠른 접근
  • 함수 종료 시 자동 해제

Heap

  • 객체, 배열, 함수
  • 크기 동적, 상대적으로 느림
  • GC가 관리
  • 참조 없으면 GC가 해제
예시
const a = 1 // Stack에 저장 (원시값) const obj = {} // Heap에 저장, Stack에는 참조(주소)만 const b = a // Stack: 값 복사 → a와 독립 const ref = obj // Stack: 주소 복사 → 같은 Heap 객체 참조

Fiber 아키텍처 React의 내부 표현

ReconciliationConcurrent Mode
React 16에서 도입된 내부 아키텍처. 각 컴포넌트를 Fiber 노드라는 단위로 표현하고, 작업을 잘게 쪼개서 중단·재개할 수 있게 함.

React 15 이전 (Stack Reconciler)

  • 재귀 호출로 동기 처리
  • 한 번 시작하면 끝까지 실행
  • 메인 스레드 블로킹
  • 큰 트리에서 프레임 드랍

React 16+ (Fiber)

  • 작업을 Fiber 단위로 쪼갬
  • 우선순위에 따라 중단·재개 가능
  • 메인 스레드를 양보할 수 있음
  • Concurrent Mode의 기반
훅 규칙과의 연결
훅을 조건문 안에 쓰면 안 되는 이유 → Fiber는 훅을 순서(인덱스)로 관리. 조건문으로 순서가 바뀌면 Fiber가 잘못된 훅 상태를 참조.

Reconciliation Virtual DOM 비교

Fiber 아키텍처Memoization
상태 변경 시 React가 이전 Virtual DOM과 새 Virtual DOM을 비교해서 실제 DOM 변경을 최소화하는 과정.

Diffing 알고리즘 규칙

  • 같은 타입이면 속성만 업데이트
  • 타입이 다르면 트리 전체 교체
  • key로 리스트 아이템 추적
  • O(n) 복잡도 (일반 트리 비교는 O(n³))

key가 중요한 이유

  • key 없으면 순서로만 비교
  • 리스트 앞에 추가 시 전체 리렌더링
  • key 있으면 같은 항목 재사용
  • 인덱스를 key로 쓰면 역효과 가능

Concurrent Mode 우선순위 기반 렌더링

Fiber 아키텍처Streaming·Suspense
Fiber를 기반으로 렌더링 작업에 우선순위를 부여하고, 급한 작업이 오면 기존 렌더링을 중단할 수 있는 모드.

주요 API

  • startTransition: 낮은 우선순위로 상태 업데이트
  • useTransition: 전환 중 isPending 상태 제공
  • useDeferredValue: 값 업데이트를 늦게 반영
  • Suspense: 데이터 로딩 중 fallback 표시

언제 쓰나

  • 검색 입력 → 결과 필터링 (입력 우선)
  • 탭 전환 → 콘텐츠 로딩 (전환 즉시 반응)
  • 대용량 리스트 렌더링 중 UI 반응성 유지
startTransition 예시
const [isPending, startTransition] = useTransition() const handleSearch = (value) => { setInput(value) // 즉시 반영 (높은 우선순위) startTransition(() => { setResults(filter(value)) // 나중에 반영 (낮은 우선순위) }) }
