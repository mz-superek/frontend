Hydration / Dehydration

RSC vs RCCStreaming·SuspenseCritical Rendering Path
SSR에서 서버가 만든 HTML에 React가 이벤트 핸들러를 붙이는 과정이 Hydration. "use client" 경계가 바로 이 구분선.

Dehydration (건조)

  • React 상태를 JSON으로 직렬화
  • HTML에 담아서 전송
  • 서버에서 일어남

Hydration (수화)

  • JSON을 브라우저에서 React 상태로 복원
  • 이벤트 핸들러 부착
  • 이 시점 전까지 클릭해도 반응 없음

Edge Runtime vs Node.js Runtime

Edge Runtime

  • CDN 가까이 실행 → 초고속
  • Node.js API 사용 불가
  • 미들웨어 기본값
  • 인증 체크, 리다이렉트에 적합

Node.js Runtime

  • 원격 서버 실행
  • 모든 Node.js API 가능
  • DB 직접 쿼리 (Prisma 등)
  • 파일 시스템 접근 가능
흔한 실수
미들웨어에서 Prisma 쓰다 에러 → Edge에서 Node.js API 호출한 것

RSC vs RCC Server Component vs Client Component

HydrationFiber 아키텍처

RSC (Server Component)

  • 기본값 (선언 없어도 RSC)
  • DB, 파일 시스템 직접 접근
  • useState, useEffect 사용 불가
  • 번들 사이즈에 포함 안 됨 → 성능 유리

RCC (Client Component)

  • "use client" 선언 필요
  • useState, useEffect 사용 가능
  • 이벤트 핸들러 사용 가능
  • Hydration 대상 → JS 번들에 포함
판단 기준
상호작용(클릭, 입력, 상태)이 필요하면 RCC. 데이터 fetching·서버 전용 로직은 RSC. 가능하면 RSC 우선 → 번들 사이즈 감소.

CORS 교차 출처 리소스 공유

Token 저장 전략CSRF·SameSite

Token 저장 전략 Cookie vs LocalStorage

OAuth·OIDCCSRF·SameSite

LocalStorage ⚠

  • JS로 자유롭게 읽기 가능
  • XSS 공격 시 토큰 탈취 가능
  • 악성 스크립트가 getItem으로 훔쳐감

  • JS에서 접근 불가
  • 서버만 읽을 수 있음
  • XSS로 훔칠 수 없음
  • CSRF 주의 → SameSite로 완화

OAuth 2.0 / OIDC 인증·인가 프로토콜

Token 저장 전략

OAuth 2.0

  • 권한 위임(Authorization) 프로토콜
  • "이 앱이 내 데이터에 접근해도 돼"

OIDC

  • OAuth 위에 인증(Authentication) 레이어
  • "이 사람이 누구인지" 신원 확인
Authorization Code Flow
① 브라우저 → IdP: 로그인 요청
② IdP → 브라우저: Authorization Code 발급
③ 브라우저 → 백엔드: Code 전달
④ 백엔드 → IdP: Code → Access Token 교환
⑤ 백엔드 → 브라우저: 세션 쿠키 발급
SaaSOps와 연결
SaaSOps가 IdP 역할 → PBU 전체 SSO를 SaaSOps IdP가 공급. 템플릿 C-3에 쓴 근거.

CSRF + SameSite 쿠키 보안

CSRF — 로그인된 사용자 모르게 악성 사이트에서 요청을 보내는 공격. 브라우저가 쿠키를 자동으로 보내는 것을 악용.

Strict

  • 다른 사이트 요청엔 쿠키 절대 안 보냄
  • 가장 안전, UX 불편

Lax (기본값)

  • 링크 클릭 등 GET만 허용
  • POST 차단, 일반적으로 권장

None

  • 모든 요청에 쿠키 포함
  • CSRF 취약, Secure 필수

V8 엔진 · JIT 컴파일 JS가 빠른 이유

가비지 컬렉션메모리 구조

JIT (Just-In-Time) 컴파일

  • 처음엔 인터프리터로 빠르게 시작
  • 자주 실행되는 코드(Hot Code) 감지
  • 감지된 코드를 머신 코드로 최적화
  • 타입이 일정하면 최적화 유지

Deoptimization (역최적화)

  • 타입이 바뀌면 최적화 코드 폐기
  • 다시 인터프리터로 돌아감
  • 예: 배열에 다른 타입 섞기
  • 타입 일관성이 성능에 직결
실무 적용
TypeScript로 타입을 일관되게 유지하면 V8이 최적화 코드를 안정적으로 유지. 배열에 타입을 섞거나 객체 shape을 동적으로 바꾸면 deopt 발생.

가비지 컬렉션 Mark & Sweep

메모리 구조V8 엔진
JS는 메모리를 자동 관리함. 참조되지 않는 객체를 탐지해서 메모리를 해제하는 과정이 GC(Garbage Collection).

Mark & Sweep 동작

  • Mark: root에서 시작해 도달 가능한 객체에 표시
  • Sweep: 표시 안 된 객체(참조 없음) 메모리 해제
  • V8은 Minor GC(Young Gen)와 Major GC(Old Gen) 분리
  • GC 실행 중 메인 스레드 멈춤 → 주의

메모리 누수 원인

  • 전역 변수에 객체 계속 추가
  • 이벤트 리스너 미제거
  • 클로저가 큰 객체 참조 유지
  • setInterval 미해제
메모리 누수 예시 vs 올바른 패턴
// ✗ 누수: 이벤트 리스너 미제거 useEffect(() => { window.addEventListener('resize', handler) }, []) // ✓ cleanup 함수로 제거 useEffect(() => { window.addEventListener('resize', handler) return () => window.removeEventListener('resize', handler) }, [])

메모리 구조 Stack vs Heap

가비지 컬렉션V8 엔진

Stack

  • 원시값 (number, boolean, string)
  • 함수 호출 정보 (실행 컨텍스트)
  • 크기 고정, 빠른 접근
  • 함수 종료 시 자동 해제

Heap

  • 객체, 배열, 함수
  • 크기 동적, 상대적으로 느림
  • GC가 관리
  • 참조 없으면 GC가 해제
예시
const a = 1 // Stack에 저장 (원시값) const obj = {} // Heap에 저장, Stack에는 참조(주소)만 const b = a // Stack: 값 복사 → a와 독립 const ref = obj // Stack: 주소 복사 → 같은 Heap 객체 참조

Fiber 아키텍처 React의 내부 표현

ReconciliationConcurrent Mode
React 16에서 도입된 내부 아키텍처. 각 컴포넌트를 Fiber 노드라는 단위로 표현하고, 작업을 잘게 쪼개서 중단·재개할 수 있게 함.

React 15 이전 (Stack Reconciler)

  • 재귀 호출로 동기 처리
  • 한 번 시작하면 끝까지 실행

  • 작업을 Fiber 단위로 쪼갬
  • 우선순위에 따라 중단·재개 가능
  • 메인 스레드를 양보할 수 있음

훅 규칙과의 연결
훅을 조건문 안에 쓰면 안 되는 이유 → Fiber는 훅을 순서(인덱스)로 관리. 조건문으로 순서가 바뀌면 Fiber가 잘못된 훅 상태를 참조.

Reconciliation Virtual DOM 비교

Fiber 아키텍처Memoization
상태 변경 시 React가 이전 Virtual DOM과 새 Virtual DOM을 비교해서 실제 DOM 변경을 최소화하는 과정.

Diffing 알고리즘 규칙

  • 같은 타입이면 속성만 업데이트
  • 타입이 다르면 트리 전체 교체
  • key로 리스트 아이템 추적
  • O(n) 복잡도 (일반 트리 비교는 O(n³))

key가 중요한 이유

  • key 없으면 순서로만 비교
  • 리스트 앞에 추가 시 전체 리렌더링
  • key 있으면 같은 항목 재사용
  • 인덱스를 key로 쓰면 역효과 가능

Concurrent Mode 우선순위 기반 렌더링

Fiber 아키텍처Streaming·Suspense
Fiber를 기반으로 렌더링 작업에 우선순위를 부여하고, 급한 작업이 오면 기존 렌더링을 중단할 수 있는 모드.

DNS · Route 53 Domain Name System

Load BalancerHTTP Cache·CDN

사람이 읽는 도메인 이름(example.com)을 컴퓨터가 쓰는 IP 주소(93.184.216.34)로 바꿔주는 인터넷의 전화번호부. 브라우저는 주소창에 도메인을 넣으면 먼저 DNS에 "이 이름의 실제 주소가 뭐야?"라고 물어본 뒤 그 IP로 접속한다. 이 조회 결과는 TTL(Time To Live) 시간 동안 캐싱되기 때문에, 레코드를 바꿔도 전 세계에 퍼지는 데(전파, propagation) 시간이 걸린다. AWS의 관리형 DNS 서비스가 Route 53이다.

자주 쓰는 레코드

  • A — 도메인 → IP 주소 직접 연결
  • CNAME — 도메인 → 다른 도메인으로 위임
  • TTL — 이 결과를 몇 초간 캐싱할지

전파가 느린 이유

  • 레코드 변경 전 값이 TTL만큼 캐시에 남아있음
  • 그래서 "바꿨는데 왜 아직 예전 걸로 뜨지?"
  • 급할 땐 배포 전에 TTL을 짧게 낮춰둠
실무에서
새 사이트를 배포하고 도메인을 연결할 때 A·CNAME 레코드를 등록하는데, "DNS 전파가 아직 안 됐다"며 반영을 기다리는 상황에서 마주친다. [클라우드·인프라]

  • 엔드포인트마다 응답 모양이 고정

N+1 쿼리 N+1 Query Problem

ORMConnection PoolRead Replica

목록을 1번 조회한 뒤, 각 항목의 연관 데이터를 항목 수(N)만큼 따로따로 다시 조회해서 쿼리가 총 N+1번 나가는 성능 문제. 예: 게시글 100개를 가져온 뒤(1번), 글마다 작성자를 개별 조회(100번) → 총 101번. ORM이 연관 데이터를 지연 로딩(lazy loading)하는 기본 동작 때문에 코드에서는 잘 안 보이고, 실제 발생한 SQL 로그를 봐야 드러난다. JOIN이나 eager loading(Prisma의 include, TypeORM의 relations)으로 한 방에 가져오게 고친다.

N+1 (문제)

  • 목록 1번 + 항목마다 1번씩 = N+1번
  • 코드는 멀쩡해 보이는데 DB만 바쁨
  • 데이터가 늘수록 선형으로 느려짐

해결

  • JOIN 또는 eager loading으로 묶어서 조회
  • IN 절로 연관 데이터 일괄 조회 후 매핑
  • 습관: ORM이 만든 SQL 로그 찍어보기
실무에서
"이 API 왜 이렇게 느리지?" 하고 로그를 열었더니 똑같은 SELECT가 수백 번 찍혀 있을 때 — 그게 N+1. 코드 리뷰에서 "여기 N+1 나겠는데요"라는 코멘트로도 자주 만난다. [백엔드]

온콜은 장애 알림을 1차로 받아 대응하는 당번. 보통 주 단위 로테이션으로 돌아가며, 근무 시간 밖이라도 알림이 오면 응답해야 한다. 에스컬레이션은 정해진 시간 안에 온콜이 응답·해결하지 못하면 다음 담당자나 상위 레벨(2차 온콜 → 팀 리드 → 매니저)로 자동으로 넘기는 절차. PagerDuty·Opsgenie 같은 도구가 이 로테이션과 에스컬레이션 정책을 관리한다.

온콜이 하는 일

  • 알림 수신(ack) → 심각도 판단
  • Runbook 보고 1차 대응
  • 해결 후 타임라인 기록 → Postmortem으로

에스컬레이션 정책 예시

  • 15분 무응답 → 2차 온콜에게 알림
  • 30분 미해결 → 팀 리드 호출
  • 고객 영향 발생 → 인시던트 채널 개설
실무에서
PagerDuty 알림이 울리면서 "지금 온콜 누구죠? 15분 무응답이면 에스컬레이션됩니다" 같은 인시던트 상황, 또는 분기마다 온콜 로테이션 표를 짜는 회의에서 마주친다. [협업·문서]

WAF Web Application Firewall · 웹 방화벽

Security GroupRate LimitingLoad Balancer

웹 애플리케이션 앞단에서 HTTP 요청의 내용을 들여다보고 SQL 인젝션, XSS 같은 웹 공격 패턴을 탐지·차단하는 보안 필터. "어느 포트·IP를 열지"만 통제하는 Security Group(네트워크 레벨)과 달리, WAF는 요청 본문·헤더·쿼리스트링까지 검사하는 애플리케이션 레벨(L7) 방어다. AWS WAF는 보통 CloudFront나 ALB 앞에 붙인다.

WAF가 막는 것

  • SQL 인젝션 · XSS 등 공격 패턴이 담긴 요청
  • 특정 IP·국가·User-Agent의 비정상 트래픽
  • 봇의 과도한 요청 (Rate-based rule)

Security Group과 차이

  • SG: "80 포트 열까 말까" — 네트워크 레벨
  • WAF: "이 요청 내용이 수상한가" — HTTP 레벨
  • 둘은 대체가 아니라 겹쳐 쓰는 관계
실무에서
"특정 IP에서 이상한 요청이 계속 들어와요" → "WAF 룰에 차단 규칙 추가합시다" 같은 보안 대응, 또는 고객사 보안 요건 문서의 "WAF 적용 여부" 항목에서 마주친다. [클라우드·인프라]

샤딩 Sharding · 수평 분할

Read ReplicaConnection Pool

데이터가 너무 많아 한 DB가 감당하지 못할 때, 데이터를 일정 기준(샤드 키 — 예: 유저 ID 범위, 해시값)으로 쪼개 여러 DB에 나눠 저장하는 수평 분할 기법. 같은 데이터를 복제해 읽기 부하만 나누는 Read Replica와 달리, 샤딩은 데이터 자체를 나누므로 쓰기 부하와 저장 용량까지 분산된다. 대신 샤드를 넘나드는 JOIN·트랜잭션이 어려워져 설계 복잡도가 크게 올라간다.

Read Replica (복제)

  • 같은 데이터를 여러 벌 복사
  • 읽기 부하 분산, 쓰기는 여전히 1곳
  • 도입 쉬움 — 먼저 시도하는 카드

샤딩 (분할)

  • 데이터를 조각내 서로 다른 DB에 저장
  • 쓰기·용량까지 분산
  • 크로스 샤드 JOIN·트랜잭션이 어려움 — 최후의 카드
실무에서
"유저 테이블이 수억 건이라 인덱스로도 한계예요, 샤딩 검토해야 할 것 같아요" 같은 대용량 서비스의 DB 확장 논의에서 마주친다. [백엔드]

SOW Statement of Work · 과업기술서

SLA·SLORFC

프로젝트에서 "무엇을, 언제까지, 어디까지 해주는지"를 명시한 계약 문서. 작업 범위(scope), 산출물(deliverables), 일정(milestones), 각자의 책임을 정의하며, 여기 적히지 않은 요청은 범위 외(out of scope)로 분류되어 추가 협의·추가 견적 대상이 된다. MSP·SI처럼 고객사 프로젝트를 수행하는 회사에서는 분쟁을 막는 기준선 역할을 한다.

SOW에 들어가는 것

  • 작업 범위와 산출물 목록
  • 일정·마일스톤·검수 기준
  • 양측 책임 (R&R)과 비용

없거나 모호하면

  • "이것도 해주시는 거 아니었어요?" 스코프 크리프
  • 검수 기준이 없어 프로젝트가 안 끝남
  • 추가 작업 비용을 청구할 근거가 없음
실무에서
킥오프 미팅에서 "그 기능은 SOW에 없는 항목이라 별도 견적입니다" 같은 범위 조율 대화, 또는 제안서·계약 단계 문서 검토에서 마주친다. [협업·문서]

배스천 호스트 Bastion Host · 점프 서버

VPCSecurity Group

외부에서 직접 접근할 수 없는 프라이빗 네트워크 안의 서버(운영 DB, 내부 API 서버 등)에 접속할 때 반드시 거쳐 가는 "관문" 서버. SSH 등 관리자 접속을 이 한 대로만 허용해 공격 표면을 줄이고, 모든 접속 기록을 한 곳에 남겨 감사(audit)도 쉬워진다. 최근에는 배스천 EC2를 직접 띄우는 대신 AWS SSM Session Manager처럼 포트를 아예 안 여는 방식으로 대체하기도 한다.

배스천이 하는 일

  • 퍼블릭 서브넷에 홀로 노출되는 유일한 진입점
  • SSH 접속 허용 IP를 한 대로 집중 관리
  • 누가 언제 들어왔는지 접속 로그 기록

없으면 생기는 일

  • 서버마다 SSH 포트를 외부에 열어야 함
  • 접속 경로가 분산돼 침입 흔적 추적 곤란
  • 보안 감사에서 지적 1순위
실무에서
"운영 DB 붙으려면 배스천 타고 들어가세요" 같은 서버 접근 안내나, VPC 구성도에서 퍼블릭 서브넷에 혼자 떠 있는 EC2로 마주친다. [클라우드·인프라]

ETL Extract, Transform, Load

Message QueueObject Storage

여러 소스(운영 DB, 로그, 외부 API)에서 데이터를 뽑아(Extract) 분석하기 좋은 형태로 가공한 뒤(Transform) 데이터 웨어하우스 등에 적재(Load)하는 데이터 파이프라인 패턴. 보통 새벽 시간에 배치(batch)로 돌며, 대시보드·리포트가 보여주는 숫자는 대부분 이 파이프라인의 산출물이다. 요즘은 일단 원본을 그대로 적재하고 나중에 가공하는 ELT 방식도 흔하다.

ETL (선가공 후적재)

  • 가공된 깨끗한 데이터만 적재
  • 웨어하우스 용량·비용 절약
  • 가공 로직 바꾸면 재수집 필요

ELT (선적재 후가공)

  • 원본을 그대로 쌓고 필요할 때 가공
  • 스키마 변경에 유연 — 클라우드 시대의 대세
  • 저장 비용은 더 들 수 있음
실무에서
"매일 새벽에 ETL 배치가 돌아서 대시보드 지표가 갱신돼요", "어제 ETL이 실패해서 오늘 리포트 숫자가 비어 있어요" 같은 데이터 지표 관련 회의에서 마주친다. [백엔드·데이터]

서비스 워커 Service Worker · PWA

Web WorkerHTTP Cache

브라우저가 페이지와 별개로 백그라운드에서 돌리는 스크립트. 페이지와 서버 사이에서 네트워크 요청을 가로채(fetch 이벤트) 캐시로 응답하거나(오프라인 지원), 푸시 알림·백그라운드 동기화를 처리한다. PWA(Progressive Web App)의 핵심 부품. 같은 "워커"지만 Web Worker는 무거운 계산을 다른 스레드로 빼는 용도, Service Worker는 네트워크 프록시 역할이라는 점이 다르다.

Service Worker

  • 네트워크 요청 가로채기 · 캐시 응답
  • 오프라인 지원, 푸시 알림
  • 페이지 닫혀도 브라우저가 깨워서 실행

Web Worker

  • 무거운 계산을 별도 스레드에서 실행
  • 메인 스레드(UI) 멈춤 방지 용도
  • 페이지가 살아있는 동안만 동작
실무에서
"배포했는데 사용자한테 예전 화면이 보여요" → 서비스 워커가 캐시한 구버전이 원인인 경우처럼, PWA·캐싱 이슈 디버깅에서 마주친다. [프론트엔드]

RTO · RPO Recovery Time Objective · Recovery Point Objective

SLARunbook

장애가 났을 때 서비스를 다시 살리기까지 허용되는 최대 시간(RTO)과, 복구 시 유실을 감수할 수 있는 최대 데이터 손실 구간(RPO)을 나타내는 재해복구(DR) 목표 지표. 예를 들어 RPO 15분이면 "최악의 경우 마지막 15분치 데이터는 사라질 수 있다"는 약속이고, 이 값이 작을수록 백업·복제 인프라 비용이 커진다. 두 숫자가 DR 아키텍처(백업 주기·복제 방식·다중 리전 여부)를 결정한다.

실무에서
"이 서비스는 RTO 4시간, RPO 15분으로 잡았어요" 같은 재해복구 계획서나 DR 훈련(Drill) 논의에서 마주친다. [클라우드·인프라]

디바운스 · 쓰로틀 Debounce · Throttle

Event LooprAF

짧은 시간에 이벤트가 연달아 발생할 때 처리 빈도를 제한하는 기법. 디바운스는 마지막 호출 후 일정 시간이 지나야 한 번 실행하고(입력이 멈추길 기다림), 쓰로틀은 일정 주기마다 최대 한 번만 실행한다(주기적으로 흘려보냄). 검색 자동완성엔 디바운스, 스크롤 위치 추적엔 쓰로틀처럼 용도가 갈린다.

디바운스

  • 마지막 이벤트 후 N ms 지나면 1회 실행
  • 입력이 계속되는 동안은 실행 안 함
  • 예: 검색창 자동완성 API 호출

쓰로틀

  • N ms 주기마다 최대 1회 실행
  • 이벤트가 계속돼도 주기적으로 실행됨
  • 예: 스크롤 위치 추적, 리사이즈 처리
실무에서
"검색창 입력마다 API가 너무 자주 불려요" → "디바운스 넣어야겠네요" 같은 입력 최적화·스크롤 이벤트 처리 논의에서 마주친다. [프론트엔드]

체인지 리퀘스트 · CAB Change Request · Change Advisory Board

RunbookADR

운영 중인 시스템을 변경(배포·설정 변경 등)하기 전에 정식 요청서(CR)를 올리고, 관련자로 구성된 승인 기구(CAB)의 검토·승인을 거치는 변경 관리 절차. "무엇을, 왜, 언제 바꾸고, 실패하면 어떻게 되돌리는지"를 사전에 문서화해 운영 사고를 줄이는 장치다. MSP처럼 고객사 시스템을 대신 운영하는 회사에서는 필수 프로세스에 가깝다.

실무에서
MSP 운영 업무에서 "이 배포는 CR 올리고 CAB 승인 받은 다음에 진행하세요" 같은 정기 배포·긴급 변경 승인 대화에서 마주친다. [협업·문서]

랜딩존 Landing Zone

IAMVPC

여러 AWS/클라우드 계정을 조직 단위로 묶어 보안·네트워크·거버넌스 기준을 미리 표준화해둔 초기 계정/환경 구조. 계정 분리 원칙, 공통 IAM·로깅·네트워크 설정을 템플릿처럼 깔아두고 시작하기 때문에, 프로젝트마다 제각각 세팅하다 생기는 보안 구멍과 운영 편차를 막아준다. AWS Control Tower가 대표적인 구축 도구.

실무에서
신규 고객사 온보딩 시 "랜딩존부터 잡고 시작하시죠" 같은 계정 구조·거버넌스 설계 논의에서 마주친다. [클라우드·인프라]

백프레셔 Backpressure

Message QueueRate LimitingDLQ

받는 쪽 처리 속도가 보내는 쪽보다 느릴 때, 넘치는 요청을 막거나 속도를 조절해 시스템이 뻗지 않게 하는 흐름 제어 방식. 수도관에서 물을 너무 세게 틀면 역압이 걸리는 것처럼, 소비자(consumer)가 감당 못 하는 만큼 생산자(producer)를 늦추거나 버퍼·큐로 완충한다. 이게 없으면 메모리가 차오르다 장애로 이어진다.

실무에서
메시지 큐나 실시간 스트림 처리량이 급증할 때 "컨슈머가 못 따라가서 백프레셔 걸어야 한다"는 대화에서 마주친다. [백엔드]

리소스 힌트 Prefetch · Preload · Preconnect

HTTP CacheCode SplittingCritical Rendering Path

브라우저에게 앞으로 필요할 리소스나 연결을 미리 준비시켜 로딩 체감 속도를 높이는 <link> 기반 최적화 힌트들. preload는 지금 페이지에 곧 필요한 리소스를 높은 우선순위로 미리 받고, prefetch는 다음 페이지에서 쓸 리소스를 한가할 때 받아두고, preconnect는 외부 도메인과의 연결(DNS·TLS)만 미리 맺어둔다. 퍼블리싱 때 쓰던 이미지 스프라이트처럼 "미리 준비"가 핵심이다.

실무에서
페이지 전환이 느리다는 피드백에 "이 리소스는 preload 걸고 다음 페이지 스크립트는 prefetch 해두자"는 성능 개선 논의에서 마주친다. [프론트엔드]

공유 책임 모델 Shared Responsibility Model

IAMSecurity Group

클라우드 인프라의 보안을 클라우드 사업자와 고객이 나눠서 책임지는 모델. AWS 등 사업자는 하드웨어·네트워크·가상화 계층 등 "클라우드 자체의" 보안을, 고객은 그 위에 올리는 데이터·설정·IAM 권한 등 "클라우드 안의" 보안을 책임진다. "S3 버킷을 퍼블릭으로 열어둬서 유출됐다"면 그건 AWS가 아니라 고객 책임 영역이라는 식으로 경계선이 갈린다.

실무에서

선행 기록 로그 Write-Ahead Log · WAL

데이터베이스가 변경 내용을 실제 데이터 파일에 반영하기 전에, 먼저 "무엇을 어떻게 바꿀지"를 순차 기록 로그(append-only log)에 먼저 적어두는 방식. 서버가 갑자기 죽어도 재시작할 때 이 로그를 다시 실행(replay)해 커밋된 변경은 복구하고 미완료 변경은 되돌릴 수 있어, ACID의 '내구성(Durability)'을 데이터 페이지를 매번 즉시 디스크에 쓰지 않고도 보장한다. 무작위로 흩어진 데이터 파일 쓰기 대신 로그에 순차 append만 하면 되므로 쓰기 성능에도 유리하다. 이 로그를 복제본에 흘려보내면 그대로 복제(replication)와 시점 복구(PITR)의 토대가 된다. PostgreSQL의 WAL, SQLite의 WAL 모드, MySQL/InnoDB의 redo log가 모두 같은 원리다.

실무에서

  • 구조 변경 적음·간단
  • 물리적 한계·다운타임·단일 장애점

  • 무상태 설계·세션 공유 필요
실무에서

인기 있는 캐시 항목이 만료되는 바로 그 순간, 그 값을 기다리던 수많은 요청이 동시에 캐시 미스가 되어 한꺼번에 원본(DB·API·연산)으로 몰려 부하가 폭증하는 현상. 평소엔 캐시가 다 막아주던 요청이 만료·서버 재시작으로 캐시가 비는 순간(콜드 스타트) 방어막이 사라져, 똑같은 값을 만들려는 무거운 작업이 수백·수천 번 중복 실행되며 DB가 넘어지기도 한다. "개 무리처럼 한꺼번에 덤빈다"고 도그파일(dog-pile), 하나의 이벤트에 다수의 프로세스가 동시에 깨어나는 더 넓은 문제를 천둥 무리(thundering herd)라고도 부른다. 완화책으로는 ① 요청 병합(single-flight·락) — 한 요청만 값을 다시 만들고 나머지는 그 결과를 기다리게 하기, ② 만료 임박 시 확률적 조기 갱신으로 만료 시점을 흩뜨리기, ③ stale-while-revalidate — 만료돼도 일단 헌 값을 주면서 뒤에서 조용히 갱신하기가 있다.

애니캐스트 Anycast

DNS·Route 53Load BalancerHTTP Cache·CDN

하나의 IP 주소를 지리적으로 떨어진 여러 서버(노드)가 동시에 광고(announce)해, 요청이 네트워크상 '가장 가까운/빠른' 노드로 자동 라우팅되게 하는 주소 지정 방식. 흔한 유니캐스트(1 IP = 1 서버)와 달리 같은 IP가 세계 곳곳에 존재하고, 라우터가 BGP 경로상 가장 가까운 곳으로 트래픽을 흘려보낸다. 덕분에 ① 지연 단축(사용자와 가까운 지점이 응답), ② 장애 대응(한 지점이 죽으면 다음 가까운 지점으로 자연스레 우회), ③ DDoS 완화(공격 트래픽이 한곳에 몰리지 않고 여러 지점에 분산 흡수)라는 이점이 있다. CDN, 공용 DNS(예: 8.8.8.8, 1.1.1.1)가 대표적으로 이 방식을 쓴다.

유니캐스트 (Unicast)

  • 1 IP = 특정 서버 1대
  • 항상 그 한 대로 도달
  • 일반적인 서버 주소 방식

애니캐스트 (Anycast)

  • 1 IP = 여러 지역 서버가 공유
  • 가장 가까운 노드로 라우팅
  • CDN·공용 DNS·DDoS 흡수

  • 항상 최신 데이터
  • 무거운 쿼리면 매번 느림

  • 결과를 물리적으로 저장
  • 읽기 빠름, 갱신 필요(REFRESH)
  • 데이터는 새로고침 시점 기준

격벽 패턴 Bulkhead Pattern

시스템 자원(스레드풀·커넥션풀 등)을 기능·의존성별로 격리해, 한 부분의 장애가 전체로 번지지 않게 하는 복원력 설계 패턴. 이름은 배의 격벽(bulkhead) 에서 왔다 — 한 구획에 물이 차도 칸이 막혀 있어 배 전체가 가라앉지 않는 원리다. 예를 들어 느려진 외부 API 호출이 공용 커넥션풀을 몽땅 붙잡아버리면 그 API와 무관한 정상 기능까지 대기하다 함께 마비되는데, 의존성마다 자원 칸(전용 풀·동시 실행 한도)을 따로 두면 한 곳이 포화돼도 나머지는 계속 돈다. 서킷 브레이커가 "고장난 호출을 아예 끊는" 것이라면, 격벽은 "고장이 번질 범위를 미리 가둬두는" 것이라 둘을 함께 쓰는 경우가 많다.

실무에서
특정 외부 연동이 느려지면 전체 서비스가 같이 죽는 문제를 겪거나, 마이크로서비스에서 장애 격리·자원 분리(전용 스레드풀·커넥션풀)를 어떻게 나눌지 설계할 때 마주친다. [백엔드·복원력]

백분위 지연시간 Percentile Latency · p95·p99

Web VitalsSLA·SLOObservability

응답 지연(latency)을 "평균"이 아니라 백분위(percentile)로 보는 지표. p99 = 전체 요청의 99%가 이 시간 안에 끝난다는 뜻이고, 뒤집으면 가장 느린 1%만 이 값보다 오래 걸린다는 의미다(p95는 상위 5%, p50은 중앙값). 평균(average)은 소수의 아주 느린 요청, 즉 꼬리 지연(tail latency)을 다른 빠른 요청들에 희석시켜 가려버리기 때문에 "다들 괜찮다"는 착시를 준다. 실제로는 그 느린 1~5%가 가장 불만이 큰 사용자이므로, 성능 목표(SLO)와 모니터링은 평균 대신 p95·p99 같은 상위 백분위를 기준으로 삼는 것이 표준이다.

실무에서
대시보드·SLO에서 "평균은 괜찮은데 p99가 튄다" 같은 성능 이슈를 진단하거나, 응답시간 알람 기준을 평균이 아닌 백분위로 잡을 때 마주친다. [성능·관측성]

합의 알고리즘 Consensus · Raft · Paxos

정족수(Quorum)분산 락결과적 일관성

여러 노드가 일부 장애·네트워크 지연 속에서도 하나의 값·순서에 똑같이 합의하도록 만드는 프로토콜. 보통 한 노드를 리더로 뽑고(리더 선출), 리더가 받은 변경 로그를 과반(quorum)의 노드에 복제해 "과반이 기록한 것만 확정"하는 식으로 일관성을 맞춘다. 이 덕분에 노드 하나가 죽어도 남은 과반이 같은 상태를 이어갈 수 있다. Raft·Paxos가 대표적이며(Raft는 이해하기 쉽게 설계된 현대적 표준), etcd·Consul·쿠버네티스 컨트롤 플레인·Kafka(KRaft)·ZooKeeper가 모두 이 원리로 클러스터 상태를 맞춘다. 클러스터를 흔히 홀수(3·5대)로 구성하는 이유도 과반을 명확히 확보하기 위해서다.

실무에서
쿠버네티스·분산 DB·메시지 큐가 "리더가 죽으면 어떻게 되나", "왜 홀수 노드로 구성하나(과반 확보)", "쿼럼을 잃으면 왜 쓰기가 멈추나" 같은 이야기를 들을 때 마주친다. [백엔드·분산]

데이터 이그레스 비용 Data Egress · 아웃바운드 전송 비용

FinOpsCDNAvailability Zone

클라우드가 자기 네트워크 "밖으로" 나가는 데이터 전송(egress·아웃바운드)에 매기는 요금. 클라우드로 들어오는 트래픽(ingress·인바운드)은 대개 무료지만, 인터넷으로 내보내는 응답·다른 리전·심지어 같은 리전의 다른 AZ(가용영역)로 나가는 데이터는 과금되는 경우가 많다. 트래픽 양에 비례해 조용히 쌓이기 때문에 예상치 못한 클라우드 비용의 단골 원인이며, 특히 대용량 파일 배포·리전 간 복제·클라우드 간(멀티클라우드) 연동에서 크게 튄다. 그래서 CDN으로 반복 트래픽을 캐시하거나, 통신하는 자원을 같은 리전·같은 AZ에 배치해 전송 구간을 줄이는 것이 대표적 절감법이다.

실무에서
클라우드 청구서에서 데이터 전송 비용이 갑자기 늘어 원인을 찾거나, CDN 활용·같은 리전 배치로 전송 비용을 줄이는 최적화를 논할 때 마주친다. [클라우드·비용]

멀티스테이지 빌드 Multi-stage Build

Cold StartImmutable InfraKubernetes

하나의 Dockerfile 안에 여러 FROM 단계(stage)를 두어, 컴파일러·개발 의존성이 필요한 '빌드 단계'와 실제 실행에 필요한 것만 담는 '최종 단계'를 분리하는 기법. 빌드 단계에서 소스를 컴파일·번들링한 뒤, 그 산출물(바이너리·정적 번들)만 최종 단계로 COPY하고 컴파일러·devDependencies·소스코드는 최종 이미지에서 버린다. 그 결과 이미지 크기가 수백 MB에서 수십 MB로 줄고, 이미지 안에 든 것이 적을수록 취약점이 노출될 공격 표면(attack surface)도 작아진다. 이미지가 가벼워지면 레지스트리 전송·배포가 빨라지고, 새 컨테이너가 뜨는 콜드 스타트도 짧아진다.

단일 스테이지

  • 이미지가 무겁고 취약점 표면 넓음
  • Dockerfile은 단순

멀티스테이지

  • 빌드 단계와 실행 단계 분리
  • 산출물만 최종 이미지로 복사
  • 슬림·보안·전송속도에 유리
실무에서
프론트엔드 앱(빌드 후 정적 파일)이나 Node 서버를 Docker로 배포할 때 무거운 이미지를 슬림하게 줄이거나, "이미지가 왜 이렇게 크냐·취약점 스캔이 많다" 같은 최적화·보안 논의를 할 때 마주친다. [인프라·컨테이너]

커서 페이지네이션 Cursor-based Pagination

GraphQLReact QueryN+1 쿼리

목록을 페이지로 나눠 줄 때 "몇 번째부터(OFFSET N)"가 아니라 "이 지점(커서) 다음부터"를 기준으로 다음 페이지를 가져오는 방식. 커서는 보통 마지막 항목의 고유값(id·정렬 키·타임스탬프)을 인코딩한 포인터다. 오프셋 방식은 페이지가 뒤로 갈수록 앞의 N개를 스캔해 버려야 해 느려지고, 조회하는 사이 데이터가 추가·삭제되면 항목이 중복되거나 누락된다. 커서 방식은 정해진 지점부터 바로 읽어 이 문제를 피하므로 대용량·실시간 목록에서 안정적이다. 대신 "5페이지로 바로 점프"나 전체 페이지 수 표시엔 약하다.

오프셋 (OFFSET/LIMIT)

  • 임의 페이지 점프·총 개수 표시 쉬움
  • 뒤 페이지일수록 느려짐
  • 데이터 변경 시 중복·누락

커서 (Cursor)

  • 항상 일정한 속도·안정적
  • 무한 스크롤·피드에 적합
  • 임의 점프·페이지 수엔 약함
실무에서
무한 스크롤·피드·대용량 목록 API를 설계하거나, GraphQL 커넥션(edges·cursor)을 다루고 "페이지 뒤로 갈수록 느리다/항목이 중복돼 보인다"는 이슈를 논할 때 마주친다. [백엔드·API]

롤링 배포 Rolling Deployment

Blue-GreenCanaryReadiness Probe

구버전 인스턴스를 한꺼번에 바꾸지 않고 몇 개씩 순차적으로 신버전으로 교체해 나가는 무중단 배포 전략. 배포 중에도 항상 일부 인스턴스가 서비스 중이라 다운타임이 없고, 블루/그린처럼 전체 환경을 두 벌 띄우지 않아 자원이 덜 든다. 대신 배포가 진행되는 동안 구·신 버전이 잠시 공존하므로 API·DB 스키마의 하위 호환이 필요하고, 문제가 생겨 롤백할 때도 다시 구버전을 순차 교체해야 해 즉시 전환(블루/그린)보다 되돌리기가 느리다. 쿠버네티스 Deployment의 기본 전략이며, 새 인스턴스가 readiness probe로 준비 완료됐는지 확인한 뒤에야 다음 것으로 넘어간다.

롤링 (Rolling)

  • 몇 개씩 순차 교체
  • 자원 추가 부담 작음
  • 구·신 공존, 롤백은 느림

블루/그린 (Blue-Green)

  • 새 환경 통째로 띄운 뒤 전환
  • 즉시 전환·즉시 롤백
  • 환경 두 벌 = 자원 2배
실무에서
쿠버네티스·오토스케일링 그룹에 새 버전을 배포하거나, "무중단 배포를 롤링·블루그린·카나리 중 무엇으로 할까"·"배포 중 구·신 버전 호환" 이슈를 논할 때 마주친다. [클라우드·배포]

연결 드레이닝 Connection Draining · Deregistration Delay

롤링 배포Load BalancerGraceful Shutdown

로드밸런서에서 인스턴스를 빼거나(배포·스케일 인) 교체할 때, 그 대상으로 새 요청은 더 보내지 않되 이미 처리 중인 요청(in-flight)은 설정한 시간 동안 끝까지 마치게 해주는 기능. 이 안전장치가 없으면 배포·스케일 인으로 인스턴스가 빠지는 순간 그 위에서 처리되던 요청이 뚝 끊겨 사용자에게 5xx 오류가 튄다. 드레이닝을 켜면 대상은 곧바로 죽지 않고 draining 상태로 들어가, 정해진 시간 동안 남은 요청을 소진한 뒤 조용히 빠진다(요청이 하나도 없으면 즉시 완료). AWS ALB에서는 이 기능을 "등록 취소 지연(deregistration delay)"이라 부르며 기본값이 300초다. 롤링·블루그린 같은 무중단 배포가 실제로 "무중단"이 되려면 이 드레이닝 시간이 요청 처리 시간보다 넉넉해야 한다.

실무에서
롤링 배포 중 "배포만 하면 잠깐 5xx가 난다"를 진단하거나, ALB 타깃 그룹에서 "등록 취소 지연을 얼마로 잡을까"·오토스케일링 인스턴스 교체 시 끊김을 논할 때 마주친다. [클라우드·배포]

도메인 주도 설계 Domain-Driven Design · DDD

MSABFFCQRS

소프트웨어를 기술 구조가 아니라 업무 도메인(비즈니스 영역) 모델을 중심으로 설계하는 방법론. 핵심은 두 가지다. ① 유비쿼터스 언어(Ubiquitous Language) — 도메인 전문가(기획·현업)와 개발자가 대화·문서·코드에서 똑같은 용어를 쓰도록 맞춰, "주문", "정산" 같은 말이 사람마다 다르게 해석되는 틈을 없앤다. ② 바운디드 컨텍스트(Bounded Context) — 큰 시스템을 의미가 뭉치는 경계로 나누고, 같은 단어라도 경계마다 다른 뜻일 수 있음을 인정한다(예: "상품"이 주문 컨텍스트와 배송 컨텍스트에서 다른 모델). 그 경계 안에서 애그리거트·엔티티·값 객체 같은 구성요소로 도메인 규칙을 코드에 담는다. 복잡한 업무 로직의 소유권을 명확히 갈라주기 때문에, MSA에서 서비스 경계를 어디서 자를지를 정하는 이론적 토대로도 자주 쓰인다.

실무에서
MSA 서비스·모듈 경계를 어떻게 나눌지 정하거나, "이 용어가 팀마다 다른 뜻으로 쓰인다"·"주문 도메인 로직을 어디에 둘까" 같은 설계 논의를 할 때 마주친다. [백엔드·아키텍처]

HTTP/3 · QUIC HTTP/3 · QUIC (RFC 9114 · 9000)

HTTP Cache · CDNWeb VitalsSSE · WS

HTTP/3는 전송 계층을 TCP가 아니라 UDP 기반의 QUIC 프로토콜 위에서 돌리는 최신 HTTP 버전(HTTP/3 = RFC 9114, 그 아래 QUIC = RFC 9000). 두 가지가 핵심 개선이다. ① 빠른 연결 수립 — 기존엔 TCP 핸드셰이크 뒤에 TLS 핸드셰이크가 따로 붙었지만, QUIC은 TLS 핸드셰이크를 연결 핸드셰이크에 통합해 주고받는 왕복을 줄인다. ② 스트림 단위 손실 처리 — HTTP/2는 한 TCP 연결에 여러 요청을 다중화하는데, 패킷 하나만 유실돼도 같은 연결의 모든 요청이 재전송을 기다리며 멈추는 TCP 레벨 head-of-line blocking이 있었다. QUIC은 UDP 위에서 손실 감지·재전송을 스트림마다 따로 하므로, 유실은 해당 스트림만 막고 나머지는 계속 흐른다. 그래서 특히 모바일·불안정한 네트워크에서 체감 성능이 좋다.

HTTP/2 (TCP)

  • TCP + 별도 TLS 핸드셰이크
  • 한 연결에 요청 다중화
  • 패킷 유실 시 전체 연결이 멈춤(HOL)

HTTP/3 (QUIC/UDP)

  • TLS 통합 → 연결 수립 빠름
  • 스트림별 손실 처리
  • 유실은 해당 스트림만 영향
실무에서
CDN 설정이나 브라우저 네트워크 탭에서 프로토콜이 h2/h3로 뜨는 걸 확인하거나, 모바일·고지연 환경 성능을 논하며 "왜 UDP 기반인데 더 안정적이냐"를 다룰 때 마주친다. [네트워크·성능]
